## 3. Why the pinned driver draft cannot be applied (reproducible)

`git apply --check` on blob `a06b7d3f…` fails:

```
error: while searching for:
#include <linux/phy/phy.h>
#include <linux/platform_device.h>
#include <linux/regulator/consumer.h>
#include <linux/reset.h>
#include <linux/slab.h>

error: patch failed: drivers/phy/qualcomm/phy-qcom-qmp-ufs.c:16
error: drivers/phy/qualcomm/phy-qcom-qmp-ufs.c: patch does not apply
```

Elimination performed before drawing a conclusion:

1. Source blob matches the patch preimage exactly (`8af777f7…`).
2. Patch context lines 16–20 are byte-identical to the file at the base commit (compared with
   `git cat-file blob` output, not by eye).
3. No CR/CRLF in the patch (`file` = ASCII text, no CR), so it is not a line-ending problem.
4. `--ignore-whitespace` and `--recount` still fail; `-C1` and `-C0` both succeed.

Root cause: the first hunk **ends on an added line** (`+#include <linux/string.h>`) with no
trailing context line. `git apply` and `patch(1)` both refuse a hunk that has no trailing context
when the added line is also the last line of the hunk body. Minimal control experiment: append one
trailing context line and widen the header to `@@ -15,7 +15,8 @@` → `git apply` succeeds.

Consequence: the locked draft is **not modified** by this Agent (it belongs to 2号 AI). The branch
already carries the equivalent, re-based artifact
`patches/round63-0001-phy-qcom-qmp-ufs-always-on.patch` (blob `99fffb10…`, 7,402 B), which is what
was applied. Equivalence to the draft is argued in the report (§3.3) on the basis of the diff body,
not on the blob hash. This matches the note recorded in `round63-ufs-phy-integration.md` §9.

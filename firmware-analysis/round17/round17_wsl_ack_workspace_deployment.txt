4. MECHANISM — WHERE THE BLOCK IS ACTUALLY DECIDED
--------------------------------------------------
4.1 The event is a first-class product event, with a stable type
The Agent keeps a per-user audit log. The exact recorded events for the two
blocked attempts are:

  category   : command-safety
  eventType  : command-safety.program-blacklist-blocked
  decision   : blocked

Same-day census of command-safety events in that log:
  command-safety.sandbox-executed            : 326  (decision=allowed)
  command-safety.program-blacklist-blocked   :   3  (decision=blocked)

So: hundreds of commands ran normally through the sandbox; exactly the WSL
attempts were rejected by a dedicated rule, not by a general failure.

4.2 The wording comes from the product, not from Windows
The shipped resource bundle contains the product's own message catalogue keys
for this exact condition:

  securityCenter.audit.commandSafety.programBlacklistBlocked
  securityCenter.audit.commandSafety.programBlacklistBlockedWithPrograms

and the panel strings:

  settings.securityCenter.detail.programBlacklistTitle = "Program Blacklist"
  settings.securityCenter.detail.programBlacklistDesc  = "Configure high-risk
     programs that must not run. Matching programs are blocked, including when
     launched by child processes. Enter only the program name, without a path
     or arguments."
  settings.securityCenter.detail.programBlacklistDescWindows = same meaning,
     "the .exe suffix is optional."
  settings.securityCenter.title = "Security Center"
  settings.securityCenter.toolControl.title = "Agent Tool Controls"

4.3 `wsl.exe` is a shipped default entry, not something the user added
The shipped bundle contains a hard-coded default program list whose members
are, verbatim:

  wsl.exe, wslconfig.exe, wmic.exe, sc.exe, reg.exe, schtasks.exe

and the matcher also derives the extension-less forms (`wsl`, `wslconfig`,
`wmic`, `sc`, `reg`, `schtasks`) from that list.

This is the decisive fact: `wsl.exe` is blocked **by product default**. It
explains why the user found no matching entry to remove and no obvious menu
naming: nothing was ever configured locally.

4.4 Local configuration contains no such entry — confirmed
  - The Agent's user settings file has `sandbox.orderedRules.command` =
    { presetVersion: 1, customized: false, rules: [] } — empty, never
    customised. The words "wsl", "blacklist", "deny" appear zero times.
  - The sandbox's own rule file has `process_rules: []` and
    `default_action: "ask"`; its only process list is a browser allow-list.
  - A bounded scan of 1,808 plain-text configuration files under the product's
    resources tree found zero occurrences of `wsl.exe`.
  => The effective blacklist is the built-in default, applied because no user
     override exists. Nothing on disk points at a user-authored rule.

4.5 Static component inspection
  - sandbox-cli.exe contains only enum-like identifiers
    (Whitelist/Blacklist/RuntimeDecision/DefaultAllow/DefaultDeny), no
    `wsl.exe` literal -> it is not the list holder.
  - The main application bundle holds the default array and the UI strings
    above, and is the origin of both the decision data and the message text.
  => Consistent with `--rule_decision center`: the "center" side (the Agent
     application) owns the list; sandbox-cli enforces it.


5. POLICY OWNERSHIP — THE ANSWER §3 ASKED FOR
---------------------------------------------
Question: is the policy user-controlled, device-admin-managed, or fixed by
host/service?

Answer: USER-CONTROLLED, per user profile, inside the Agent application.

Supporting reasoning:
  - The list is exposed as an explicit, editable settings panel with an
    "Add" action and a helper text that tells the user to "enter only the
    program name". That is a configuration surface, not a fixed policy.
  - The storage location is the per-user Agent settings/audit area, under the
    current user profile — not a machine-wide policy store, not a domain GPO,
    not an MDM channel.
  - No enterprise-policy marker was found; the settings file's command rule
    group reports `customized: false`, which only makes sense for a
    user-editable layer that has not yet been edited.
  - The prior ROUND16 guess named a Windows OS location. That was wrong and is
    formally withdrawn: the owning UI belongs to the Agent application, and
    the OS-level security stack is not involved.

6. WHY THE ROUND16 MESSAGE LOOKED LIKE AN OS SECURITY BLOCK
-----------------------------------------------------------
The enforcement message is intentionally phrased in generic security language
("blocked by security policy", "cannot be bypassed from the current command")
and it told the operator to change a setting in a "Security Center". Both
statements are literally true of the Agent's own Security Center — but they
read like an OS-level control, which is what misled the previous task book into
guessing a Windows menu.

Recorded for the audit trail: the guessing failure was in the task book, not in
the observed machine state. ROUND16's machine facts were correct; only its
attribution of ownership was wrong, and this round corrects it.

2.4 Entry point arithmetic, verified three ways

  Route 1 - the PE field itself:      AddressOfEntryPoint = 0x23D7C40
  Route 2 - vmlinux symbol table:     __efistub_efi_pe_entry @ 0xFFFFFFC0823D7C40
                                      minus kernel base 0xFFFFFFC080000000
                                      = 0x23D7C40
  Route 3 - the linker expression:    arch/arm64/kernel/efi-header.S:49 writes
                                      .long __efistub_efi_pe_entry - .L_head
                                      and .L_head is the first byte of _text, whose
                                      VA is 0xFFFFFFC080000000 (System.map: _text)

  All three agree to the byte. The address translation also explains why a naive
  System.map lookup of "0x23D7C40" fails: System.map carries kernel VAs, not RVAs,
  and it additionally contains absolute-type linker symbols (type 'A') such as
  __pecoff_data_size = 0x3B0000 which must be excluded from any address search.
  Doing that exclusion is what makes the lookup land on __efistub_efi_pe_entry.

  Note also where the entry lives: 0x23D7C40 sits above __init_begin (VA
  0xFFFFFFC082370000), i.e. inside .init.text. That is not an anomaly - it is the
  direct consequence of the objcopy invocation discussed in 2.6.

================================================================================
3. WORK PACKAGE B - MEMORY HANDOFF ROUTE
================================================================================

The question this package answers: given ROUND19's finding that the stock base DTB
/memory reg is an all-zero placeholder, does an EFI-capable Image give a real
conditional workaround? Yes - and the reason is a single explicit function.

3.1 Normal arm64 route (no EFI): /memory is the only source, and zero size is fatal

  arch/arm64/kernel/head.S:45-51 states the entry contract:
      /*
       * The requirements are:
       *   MMU = off, D-cache = off, I-cache = on or off,
       *   x0 = physical address to the FDT blob.
       */

  arch/arm64/kernel/head.S:170-185 (preserve_boot_args) takes x0 into x21 and
  stores all four arguments:
      mov  x21, x0                 // x21=FDT
      adr_l x0, boot_args
      stp  x21, x1, [x0]
      stp  x2, x3, [x0, #16]

  arch/arm64/kernel/head.S:231, inside __primary_switched:
      str_l x21, __fdt_pointer, x5   // Save FDT pointer

  arch/arm64/kernel/setup.c:61      phys_addr_t __fdt_pointer __initdata;
  arch/arm64/kernel/setup.c:88      u64 __cacheline_aligned boot_args[4];
  arch/arm64/kernel/setup.c:293     setup_machine_fdt(__fdt_pointer);
  arch/arm64/kernel/setup.c:373-377 warns if boot_args[1..3] are non-zero, i.e. it
  expects a bootloader to pass a zeroed x1..x3.

  setup_machine_fdt (setup.c:170-208) remaps the FDT and calls early_init_dt_scan at
  :183. If that returns false the kernel does not panic in any civilised way - it
  prints a pr_crit and spins:
      while (true)
          cpu_relax();
  Note the distinction: this failure is "invalid DTB", not "no memory in DTB". An
  all-zero /memory reg is a perfectly valid DTB, so this path is taken normally.

  drivers/of/fdt.c:1041-1088 (early_init_dt_scan_memory) then walks subnodes:
      :1048   if (type == NULL || strcmp(type, "memory") != 0) continue;
      :1054   reg = "linux,usable-memory" if present, else "reg"
      :1069   base = dt_mem_next_cell(dt_root_addr_cells, &reg);
      :1070   size = dt_mem_next_cell(dt_root_size_cells, &reg);
      :1072   if (size == 0) continue;            <-- the zeroed-reg case
      :1076   early_init_dt_add_memory_arch(base, size);
      :1078   found_memory = 1;

  So a /memory node whose reg is 0/0/0/0 is skipped silently, found_memory stays 0,
  and nothing enters memblock. early_init_dt_add_memory_arch itself is the generic
  weak definition at drivers/of/fdt.c:1177, which pages the range and adds it to
  memblock.

  Then arch/arm64/mm/init.c:205-310 arm64_memblock_init runs, and it is important
  what it does NOT do: it contains no memblock_add of discovered RAM. Every call in
  it is a remove, a limit, or a reserve - :224 memblock_remove above the PA size,
  :240 memblock_remove beyond the linear map, :246 memblock_remove below
  memstart_addr, :265 memblock_mem_limit_remove_map, :302 memblock_reserve for the
  kernel image. The only adds are repairs (:266 the kernel itself, :292 the initrd)
  so that the kernel and initrd stay reachable after clipping.

  Consequence for the plain route: with an all-zero /memory and no EFI, memblock has
  no memory. bootmem_init (init.c:312-317) then derives min/max purely from
  memblock_start_of_DRAM()/memblock_end_of_DRAM() of an empty set. Nothing in the
  arm64 source inspected here invents memory from anywhere else on that route. That
  is why ROUND19's finding is blocking rather than cosmetic.

3.2 EFI route: memblock is wiped and rebuilt from the UEFI memory map

  setup_arch (arch/arm64/kernel/setup.c:282-345) orders the calls as:
      :293  setup_machine_fdt(__fdt_pointer)     -> scans DT, memblock may stay empty
      :324  efi_init()
      :333  arm64_memblock_init()
      :345  bootmem_init()
  The ordering is the whole argument: efi_init() runs BEFORE arm64_memblock_init(),
  so whatever efi_init() puts into memblock is what arm64_memblock_init() then
  clips.

  drivers/firmware/efi/efi-init.c:159-231 reserve_regions() is the decisive code:

      :167-173  /*
                * Discard memblocks discovered so far except for KHO scratch
                * regions. Most memblocks at this point originate from memory nodes
                * in the DT and UEFI uses its own memory map instead. ...
                */
      :186-193  } else {
                    /*
                     * KHO is disabled. Discard memblocks discovered so far:
                     * if there are any at this point, they originate from memory
                     * nodes in the DT, and UEFI uses its own memory map instead.
                     */
                    memblock_remove(0, PHYS_ADDR_MAX);
                }
      :195-230  for_each_efi_memory_desc(md) {
                    ...
                    if (is_memory(md)) {
                        if (efi_soft_reserve_enabled() &&
                            (md->attribute & EFI_MEMORY_SP))
                                continue;
      :221              early_init_dt_add_memory_arch(paddr, size);
                        if (!is_usable_memory(md))
      :224                  memblock_mark_nomap(paddr, size);
                        if (md->type == EFI_ACPI_RECLAIM_MEMORY)
      :228                  memblock_reserve(paddr, size);
                    }
                }

  Three things follow, all from the same function:
    (a) Any DT-derived memory is explicitly thrown away (:192), with a comment that
        names the DT memory nodes as the thing being thrown away.
    (b) Memory is rebuilt from the UEFI descriptors (:221) using the very same
        helper that early_init_dt_scan_memory uses, so it lands in memblock the same
        way and is indistinguishable downstream.
    (c) The zeroed /memory reg therefore cannot hurt on this route, because the DT
        values are discarded before they could matter.

  This is the answer to "does EFI-stub boot proceed without a usable /memory/reg":
  yes, provided EFI is actually in play, and it is not a lucky side effect but an
  explicit design statement in the source.

3.3 What efi_init() requires before any of that happens

  drivers/firmware/efi/efi-init.c:233-278
      :239  efi_system_table = efi_get_fdt_params(&data);
      :240-241  if (!efi_system_table) return;      <-- silent fall back to DT path
      :243-250  if (efi_memmap_init_early(&data) < 0) panic("Unable to map EFI
                                                          memory map.\n");
      :261  reserve_regions();
      :271  memblock_reserve(data.phys_map & PAGE_MASK, ...);

  The comment at :244-248 is unambiguous: "If we are booting via UEFI, the UEFI
  memory map is the only description of memory we have, so there is little point in
  proceeding if we cannot access it." That panic is the only hard failure in the
  path, and it triggers on an unmappable map, not on a missing /memory node.

  drivers/firmware/efi/fdtparams.c:84-133 efi_get_fdt_params is where the
  metal meets the FDT:
      :49    .path = "/chosen",
      :51-55 "linux,uefi-system-table", "linux,uefi-mmap-start",
             "linux,uefi-mmap-size", "linux,uefi-mmap-desc-size",
             "linux,uefi-mmap-desc-ver"
      :103-104 if (!fdt) return 0;
      :115-125 walk the five names; the first one (system table) is mandatory,
               the rest are required if the first is present
      :130-132 notfound: pr_info("UEFI not found.\n"); return 0;

  So the entire EFI route hinges on five properties in /chosen. Without them the
  kernel prints "UEFI not found." and behaves as a plain DT kernel - which, with a
  zeroed /memory, is exactly the failing case. This is the fork in the road.

3.4 Who writes those five properties, and what happens if nobody does

  Two producers exist in this tree.

  Producer 1 - the bootloader, directly. fdtparams.c is only a consumer; ARCH code
  must have put the values there. This is the route a stock HOS bootloader could
  take without ever entering the PE entry.

  Producer 2 - the EFI stub itself, at drivers/firmware/efi/libstub/fdt.c:30-145
  update_fdt(). It writes, and only writes:
      :88-93    bootargs
      :99       linux,uefi-system-table
      :105      linux,uefi-mmap-start     (placeholder U64_MAX)
      :111      linux,uefi-mmap-size      (placeholder U32_MAX)
      :115      linux,uefi-mmap-desc-size (placeholder U32_MAX)
      :119      linux,uefi-mmap-desc-ver  (placeholder U32_MAX)
      :123-133  kaslr-seed
  and later :147-182 update_fdt_memmap() patches the four mmap placeholders in place
  with the real values once boot services are being exited.

  Critically, update_fdt() writes NO /memory node. It cannot: an EFI application has
  no business editing the platform's memory description when the kernel will read
  the UEFI map instead. What it does do is delete the reserve map:
      :70-76  /*
               * Delete all memory reserve map entries. When booting via UEFI,
               * kernel will use the UEFI memory map to find reserved regions.
               */
              while (num_rsv-- > 0) fdt_del_mem_rsv(fdt, num_rsv);
  which is the same statement in a different form: on this route the UEFI map
  supersedes the FDT's memory information.

  Where does the stub get its DTB? libstub/fdt.c:222-288
      :235-241  allocate a virtmap (needs the UEFI map)
      :249-260  the dtb= command line is honoured ONLY if
                CONFIG_EFI_ARMSTUB_DTB_LOADER is enabled AND secure boot is
                disabled. This tree has that option off (2.1), so dtb= is ignored
                and an "Ignoring DTB from command line." message is printed.
      :262-269  otherwise ask the firmware: get_fdt() reads the DEVICE_TREE_GUID
                configuration table, and prints "Using DTB from configuration table"
      :271-272  if there is still no DTB: "Generating empty DTB"
      :276-283  allocate MAX_FDT_SIZE and update_fdt() into it

  The "Generating empty DTB" branch matters a great deal for this device. If ABL
  enters the PE entry but does not publish a DEVICE_TREE_GUID table, the stub will
  hand the kernel a syntactically valid but EMPTY tree. That tree has no
  /firmware/android/fstab, no /firmware/android/vbmeta, no /rootparam, no /memory,
  and none of the nine board variants' properties. The kernel would then fall back
  to the UEFI map for memory (fine) but would have lost the entire DT fstab that
  ROUND19 established is the only first-stage mount description in this firmware.
  An empty DTB is therefore not a neutral outcome; it is a different failure mode.

3.5 How control actually passes, and the DTB pointer contract

  libstub/arm64.c:131-139
      void __noreturn efi_enter_kernel(unsigned long entrypoint,
                                       unsigned long fdt_addr,
                                       unsigned long fdt_size)
      {
          void (* __noreturn enter_kernel)(u64, u64, u64, u64);
          enter_kernel = (void *)entrypoint + primary_entry_offset();
          enter_kernel(fdt_addr, 0, 0, 0);
      }

  So the stub jumps to primary_entry (via the offset from arm64-stub.c:48) with
  x0 = fdt_addr and x1..x3 = 0 - which is precisely the contract in head.S:45-51
  and precisely what setup.c:373-377 expects to be zero. The EFI route and the
  plain route converge on the same kernel entry; they differ only in what the FDT
  contains and in whether boot services were exited.

  This is worth stating plainly because it is a natural misconception: entering via
  EFI does not put the kernel on some separate "EFI-only" code path. It arrives at
  primary_entry identically. The difference is entirely in memblock's provenance.

3.6 Decision tree

  Does the loader jump to .L_head (file offset 0, the "MZ" trick)?
  |
  +-- NO. It jumps to primary_entry with x0 = DTB. This is the plain arm64 route,
  |   and it is the route the stock kernel must use, because the stock kernel has
  |   no PE header (section 4.4).
  |     |
  |     +-- /memory reg usable (size != 0)
  |     |     -> memblock populated from the DT -> proceeds
  |     |
  |     +-- /memory reg all zero (ROUND19's finding)
  |           -> of/fdt.c:1072 skips it, so memblock gets nothing from the DT
  |           -> arm64_memblock_init (init.c:205-310) adds nothing of its own
  |           |
  |           +-- /chosen HAS linux,uefi-mmap-*
  |           |     -> efi_init() still runs and REPLACES memblock from the UEFI
  |           |        map (efi-init.c:192 then :221) -> may proceed after all
  |           |
  |           +-- /chosen has NO such properties
  |                 -> "UEFI not found." (fdtparams.c:130-132), efi_init returns
  |                    early (efi-init.c:240-241), memblock stays empty, and no
  |                    remaining source can supply memory -> blocking
  |
  +-- YES. The firmware loads this Image as an EFI application. Possible only for a
      payload that has a PE header, i.e. the ROUND18 Image and not the stock kernel.
        |
        +-- UEFI system table invalid -> efi_pe_entry returns EFI_INVALID_PARAMETER
        |   (efi-stub-entry.c:46-47) and nothing boots
        |
        +-- system table valid, then three questions in order:
              (1) CONFIG_EFI_ARMSTUB_DTB_LOADER is off here (2.1), so any dtb= on
                  the command line is ignored (libstub/fdt.c:249-253)
              (2) is a DEVICE_TREE_GUID configuration table published?
                    yes -> that DTB is used and /firmware/android/* survives
                    no  -> "Generating empty DTB" (libstub/fdt.c:271-272), which is
                           a NEW failure mode: /memory is covered by the UEFI map,
                           but /firmware/android/fstab is gone, so the first stage
                           has no mount description at all
              (3) regardless of (1) and (2), reserve_regions() discards whatever the
                  DT said about memory and rebuilds it from the UEFI map
                  (efi-init.c:192, :221) -> the zeroed /memory reg stops mattering

3.7 Exact ABL-side proof still missing

  Everything above is kernel-side. To convert layer 3 of the verdict from UNKNOWN to
  known, one of the following would be needed, and none is available offline:
    - abl.img, or its EFI loader module, showing whether the kernel partition is
      dispatched through an EFI application path or a raw jump;
    - a UART/XBL log from a boot attempt showing "Booting Linux Kernel..." or
      "UEFI not found." - the stub prints the first, efi_get_fdt_params prints the
      second, and their presence or absence is a direct observation of the route;
    - the device's own device-tree handoff dump showing whether a
      DEVICE_TREE_GUID table exists before the kernel runs;
    - the ABL's decompression path, which section 4 shows must exist for stock.

  Until then the honest statement is: the Image is EFI-capable; whether the platform
  uses that capability is unproven either way.

4.2 Classification

  Magic 1f 8b 08 matches the gzip family. file(1) agrees, independently:
    "gzip compressed data, max compression, from Unix,
     original size modulo 2^32 57470992"

  The ten-byte header decodes as:
    1f 8b    magic
    08       CM = deflate
    00       FLG = 0        -> no FNAME, no FEXTRA, no FCOMMENT, no FHCRC
    00000000 MTIME = 0      -> no timestamp, i.e. reproducible
    02       XFL = 2        -> maximum compression
    03       OS = 3         -> Unix

  A raw arm64 Image would instead begin with the "MZ"-style code0 bytes. This
  payload does not; an in-place probe for the ARM64 magic at offset 0x38 returns
  no. So the stock kernel payload is a compressed container, not a bare Image.

  Therefore: gzip. Not LZ4 (would be 04 22 4d 18), not XZ (fd 37 7a 58 5a 00), not
  zstd (28 b5 2f fd), not lzma alone (5d 00 00), not bzip2 (BZh).

4.3 Decompression and re-probe

  Decompresses cleanly with the installed gzip to 57 470 992 bytes
  (sha256 first16 cf21f9d22c45752a). The decompressed buffer is a valid arm64
  Image:

    magic @0x38    0x644D5241  ("ARMd")            -> valid
    text_offset    0x80000     (524 288)
    image_size     0x433D000   (70 504 448)
    flags          0xA         -> little-endian, 4 KiB, PHYS_BASE set
    res5 @0x3c     0x0         -> NO PE header

  file(1) on the decompressed buffer confirms independently:
    "Linux kernel ARM64 boot executable Image, little-endian, 4K pages"

  The 13 033 456-byte gap between the 57 470 992-byte file and the 70 504 448-byte
  image_size is BSS, the same phenomenon as in 2.2 and not an anomaly.

4.4 The single most important field in this comparison

  res5 at offset 0x3c is the PE header offset. In the ROUND18 Image it is 0x40, and
  a complete PE/COFF EFI application follows. In the decompressed STOCK kernel it is
  0x0, meaning no PE header was emitted at all.

  arch/arm64/kernel/efi-header.S:11-25 explains why: the whole PE header block is
  inside #ifdef CONFIG_EFI, and the "MZ" code0 only appears in that case; otherwise
  the same site emits an ordinary nop. The stock kernel therefore was built without
  CONFIG_EFI, and - this is the operational consequence - the stock kernel CANNOT
  be entered as an EFI application. Whatever route the stock device takes, it is the
  plain arm64 route of section 3.1, not the EFI route of 3.2.

  That is a genuinely new result for this project: ROUND19 showed the stock DTB has a
  zeroed /memory and no DTBO fixes it; section 4 now shows the stock kernel could not
  have taken the EFI escape hatch even if the platform offered it. The stock kernel
  must therefore be getting memory from somewhere this audit has not found, or the
  /memory node seen in the base DTB is not the one the bootloader finally passes.
  That is recorded as U-3, and it is a sharper form of the ROUND19 question than
  "who fills /memory" - it is "who fills /memory, given that the escape hatch is
  provably absent on stock".

  Also worth noting, and it constrains the loader: text_offset is 0x80000 here and
  0x0 in the ROUND18 Image, but both set the PHYS_BASE flag bit (flags 0xA in both
  cases, decoded against image.h:8-21). PHYS_BASE means the image is loadable at any
  physical address and text_offset is not the load contract. The two images do not
  disagree about load address; they both opt out of a fixed one. Whether the loader
  honours that bit is U-6.

4.5 Sibling payloads in the same container, sizes only

  Boot ramdisk @22 269 952, 519 986 bytes, first four bytes 1f 8b 08 00 - also gzip.
  DTB @22 790 144, 1 664 243 bytes, magic d0 0d fe ed with fdt_totalsize 556 524,
  i.e. the real tree occupies 556 524 of the 1 664 243 bytes reserved for it; the
  remainder is padding to the slot, consistent with ROUND19.
  payload_end 24 457 216, dtb_end 24 454 387, so 2 829 bytes of alignment tail.

  No kernel binary was uploaded, embedded or reproduced in this report; only header
  bytes, sizes and digests appear, as the task requires.

5.7 What this arithmetic does and does not prove

  It proves: both candidate payloads fit inside a 96 MiB partition with room to
  spare, and the gzip variant is smaller than the stock image the vendor ships, so
  size is not a reason the gzip variant would be rejected on capacity grounds.

  It does NOT prove any of the following, and none of them should be read into the
  numbers above:
    - that the resulting container would be AVB-valid. It would not be: the stock
      footer signs original_image_size 24 457 216 over a specific hash of the
      specific bytes. Changing the payload invalidates it. No footer or vbmeta was
      copied, re-signed or even opened during this calculation.
    - that ABL would accept a payload of a different size or a different kernel.
      Acceptance policy is ABL behaviour, and ROUND19 established there is no ABL
      binary in the extraction to inspect.
    - that raw would work. A raw payload is a legitimate arm64 Image, but this
      loader is known to be fed gzip on stock (section 4), so whether it also
      accepts raw is unverified. A loader that blindly gunzips would fail on raw; a
      loader that sniffs would accept both. Nothing here distinguishes them.
    - that gzip is required. The stock payload being gzip establishes that the
      loader CAN handle gzip. It does not establish that the loader requires gzip.
      Per the task instruction, the gzip requirement is therefore labelled
      "compatibility unverified", not "required".

  One additional inference is safe and worth stating: an arm64 Image has no
  self-decompression. CONFIG_EFI_ZBOOT is off in this tree (2.1), and the classic
  arm64 boot contract in head.S:45-51 assumes an already-decompressed image at the
  entry point. Since the stock kernel sits in the partition as gzip and cannot
  decompress itself, the stock loader must be doing the decompression. That is a
  positive, if indirect, statement about ABL capability - and it is the closest this
  round gets to evidence about ABL behaviour from a purely offline artefact.

    assert is that a kernel-side prerequisite that the stock kernel almost certainly

    $OUT/.config:3417   CONFIG_PINCTRL=y          (framework only)
    $OUT/.config:3430   CONFIG_PINCTRL_SINGLE=y   (trivial single-node driver only)

    drivers/pinctrl/qcom/Kconfig:4 declares the driver as "config PINCTRL_MSM", and
    that symbol is explicitly unset. So the tree has the pinctrl core and one
    generic stub driver, but no Qualcomm TLMM driver. Any pinmux/pinconf state
    described in the board DTS for SM8250 pins has no consumer.

    Whether UFS actually needs pinctrl at runtime depends on whether the stock
    bootloader leaves the UFS pins in a usable state and on what the DTS asks for.
    I did not audit the DTS pin states this round (work package E explicitly says
    not to touch board DTS). So this is recorded as a gap with an open dependency,
    not as a proven blocker.

  Two lesser items, recorded for completeness rather than alarm:
    CONFIG_QCOM_SMEM is not set, and CONFIG_QCOM_SMD_RPM is not set, while
    CONFIG_QCOM_SMEM_STATE=y. SMEM is the shared-memory transport used by some
    Qualcomm subsystems; UFS does not go through it on this platform, and RPMh-based
    clock/pd/interconnect are all present, so the storage path does not appear to
    depend on it. Worth confirming before any boot attempt, not worth calling a
    blocker.
    CONFIG_ARM_SMMU_V3 is not set. SM8250 uses SMMU-500 (v2), which is covered by
    CONFIG_ARM_SMMU=y. Consistent.
    CONFIG_DM_VERITY_VERIFY_ROOTHASH_SIG is not set. Signature-checked verity
    root hashes are an Android verified-boot hardening feature; the DT fstab uses
    fsmgr_flags "wait,logical,avb", which is the AVB path, not the roothash-sig
    path. Not expected to be needed.

6.3 Monolithic, proven without rebuilding

  The task asks to verify that the Image is built-in for these drivers rather than
  relying on .ko modules, without rebuilding. Four independent observations:

    $OUT/.config:919                CONFIG_MODULES=y  (module support compiled in)
    $OUT/Module.symvers             0 bytes - no exported symbols at all
    $OUT/modules_staging_dir.tar.gz 67 bytes, containing exactly one entry: ./
    find $ACK/bazel-bin -name '*.ko'  0 results

  A build with CONFIG_MODULES=y that produces zero modules, an empty staging tar and
  an empty Module.symvers can only have everything linked into the Image. Combined
  with the symbol counts in 6.1, this is conclusive: UFS, QMP UFS PHY, RPMh
  clock/pd, interconnect, SMMU, dm-verity, EROFS and ext4 are all in the monolithic
  kernel.

  (CONFIG_ANDROID_BINDER_IPC_RUST=m appears in .config as a module request but no
  .ko exists, so it too did not materialise; it is irrelevant to the storage path.)

6.4 Cross-check against the ROUND19 ramdisk inventory

  ROUND19 established, and the inventory re-read this round confirms:
    ramdisk.img payload  gzip, 1 322 962 bytes on disk, 2 884 352 decompressed
    CPIO format          newc, 17 entries
    contents             AArch64 ELF /init (2 880 584 B), /patch_avb_key (520 B),
                         system/etc/ramdisk/build.prop (942 B), 13 empty dirs
    key_hits.modules_load   0
    key_hits.kernel_module  0
    key_hits.fstab          0
    key_hits.ueventd        0
    key_hits.init_rc        0
    key_hits.first_stage_rc 0
    key_hits.selinux_policy 0

  The cross-check is consistent in both directions:
    - No modules.load and no modules directory means the first stage cannot load any
      .ko. That is only survivable if the drivers are built in - which 6.3 proves
      they are, for the storage chain.
    - No text fstab in the ramdisk matches ROUND19's finding that the fstab lives in
      the base DTB at /firmware/android/fstab with system/vendor/odm entries, each
      in ext4 and erofs flavour, fsmgr_flags "wait,logical,avb". Every flag there is
      served by a built-in driver in 6.1 (dm-verity, logical partitions, erofs/ext4).
    - No ueventd, no *.rc and no sepolicy in the ramdisk means all of that is
      userspace-side and comes from the system image, not from the boot chain. It
      also means the boot chain contributes nothing that could create /dev, which is
      exactly why Finding E-1 deserves attention.

  One asymmetry worth naming: the DT fstab is only reachable if the DTB survives to
  the kernel. On the plain route that is automatic. On the EFI route it depends on
  the loader publishing a DEVICE_TREE_GUID table, else the stub generates an empty
  tree and the fstab is gone (section 3.4). So Finding E-1 and the empty-DTB branch
  are two different ways to arrive at "first stage has no block devices", and they
  compound rather than overlap.

6.5 Remaining boot-critical unknowns (unchanged by this round unless noted)

    - effective DTB / UFS node state at runtime. ROUND19 showed the base DTB's UFS
      node exists; what the nine DTBO variants do to it per board-id was not
      re-audited (and must not be, this round).
    - PMIC parent-supply chain for the UFS rails. REGULATOR_QCOM_RPMH is in, but the
      actual supply tree is DTS data and was not inspected.
    - ARC / proxy handoff for the UFS PHY. qmp_ufs_* is linked, but whether the
      firmware hands over the PHY in a state this driver accepts is a runtime fact.
    - which rootparam overlay the loader selects (ROUND19: nine variants VA..VI,
      board-id 0x2008..0x206e, each writing five properties into /rootparam).
    - memory handoff, i.e. section 3 - now sharper: see U-3.
    - AVB. Any payload change invalidates the footer, and no signing was performed
      or possible this round.
    - NEW this round: CONFIG_DEVTMPFS (E-1) and CONFIG_PINCTRL_MSM (E-2).

7. UNKNOWNS
================================================================================

Each entry states what is unknown, why it is unknown, and exactly what would settle
it. None of them is papered over elsewhere in this report.

U-1  Whether Huawei ABL reaches the PE/COFF entry at all.
     This is the gap between verdict layer 2 (established) and layer 3 (not).
     Needed: abl.img or the EFI loader module from the boot chain; or a UART/XBL log
     from a boot attempt. The stub prints "Booting Linux Kernel..." on entry, which
     would settle it in one line if such a log existed. ROUND19 confirmed there is
     no abl.img in the extraction, so this round had nothing to read.

U-2  Whether ABL publishes a DEVICE_TREE_GUID configuration table.
     Only relevant if U-1 resolves to "yes", but the consequence is severe either
     way: per libstub/fdt.c:271-272, a loader that enters the stub without a DTB
     gets an empty tree, and an empty tree has no /firmware/android/fstab, so the
     first stage loses its only mount description. Also note that
     CONFIG_EFI_ARMSTUB_DTB_LOADER is off here, so the dtb= command line is not an
     available workaround.
     Needed: a DT dump taken by the stub, or the device's UEFI configuration table
     list before kernel entry.

U-3  How the stock kernel obtains memory, given that it cannot be an EFI application.
     New this round and it sharpens ROUND19's U-1 considerably. ROUND19 asked "who
     fills the zeroed /memory". Section 4.4 now shows the stock kernel has res5 = 0,
     i.e. no PE header, so the EFI escape hatch of section 3.2 was never available to
     it. Therefore either (a) something else fills memory on the plain route, or (b)
     the /memory node present in the extracted base DTB is not the node the
     bootloader finally hands over - the extracted DTB may be the template, with the
     loader patching reg before entry. Option (b) would make ROUND19's zeroed reg a
     property of the file rather than of the running system.
     Needed: a runtime FDT dump from the device, or the loader's DT fixup code.
     This is now the highest-value open item in the memory question, because it
     decides whether the whole /memory problem is real or an artefact of extracting
     a template.

U-4  Whether ABL decompresses, and whether it requires gzip specifically.
     Established indirectly: stock ships gzip and an arm64 Image cannot decompress
     itself (CONFIG_EFI_ZBOOT off), so the loader must decompress. Not established:
     whether the loader insists on gzip. A sniffer would also accept raw; a blind
     gunzip would not.
     Needed: the loader's image-loading code, or a boot log showing the handover.

U-5  Whether the CONFIG_DEVTMPFS gap (E-1) actually blocks the first stage.
     The kernel side is proven absent (0 devtmpfs symbols). The userspace side was
     not audited: Android's first stage may cope by creating nodes in a tmpfs, or it
     may not. I am not asserting failure.
     Needed: read the first-stage logic inside the stock /init ELF, or test with a
     kernel that differs only in this option. The former is a static-analysis job
     on an already-extracted binary and is the cheaper next step.

U-6  Whether the loader honours the PHYS_BASE flag and ignores text_offset.
     Both the stock kernel (text_offset 0x80000) and the ROUND18 Image (text_offset
     0x0) set PHYS_BASE in flags 0xA, so per image.h:8-21 neither declares a fixed
     load offset. If the loader instead honours text_offset literally, the two
     images would disagree about where to place the kernel.
     Needed: the loader's Image-header handling, or a runtime observation of the
     load address.

U-7  Whether the missing PINCTRL_MSM driver (E-2) blocks UFS.
     Depends on whether the UFS node's pinctrl states are actually needed and on
     what state the bootloader leaves the pins in. The board DTS was deliberately
     not inspected this round.
     Needed: a DTS-side check of the UFS node's pinctrl-0/-1 states, in a round that
     is allowed to read the DTS.

U-8  The provenance of the 96 MiB partition capacity used in section 5.
     The figure is taken from the task and used as given. It was not re-derived from
     a partition table this round, and the earlier rounds' GPT/LP work was not
     repeated by instruction.
     Needed: nothing new if the task's figure is authoritative; otherwise the GPT
     entry for the boot partition.

7.1 Summary of what changed in the project's picture this round

  Turned from assumption into measurement:
    - the Image is EFI-stub capable and carries a real EFI application PE header,
      with the entry point provable three ways;
    - the stock kernel is NOT EFI-stub capable (no PE header);
    - the stock kernel payload is deterministic max-compression gzip;
    - the EFI route provably discards DT-derived memory and rebuilds from the UEFI
      map, which is the exact mechanism that would neutralise the zeroed /memory.

  Newly visible gaps:
    - CONFIG_DEVTMPFS off and CONFIG_PINCTRL_MSM off in the ROUND18 build;
    - an empty-DTB branch in the stub that would silently cost the DT fstab;
    - U-3, which questions whether the zeroed /memory is a runtime fact at all.

  Explicitly NOT claimed: no boot, no DTB, no boot package, no AVB result, no
  device interaction, no milestone of any kind.

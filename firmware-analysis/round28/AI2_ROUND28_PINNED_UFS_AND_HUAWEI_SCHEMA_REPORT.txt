4. WORK PACKAGE D - UFS PROPERTY DECISION TREE (NO DTS CHANGE)
------------------------------------------------------------------------------
Question: what to do with vcc-voltage-level in the board DTS?

Established facts (pinned ACK + ROUND27 DTB evidence):
  - Fixed ACK generic UFS driver does NOT parse vcc-voltage-level (1.3).
  - The driver tracks only max_uA current and sends regulator_set_load() +
    enable/disable; no voltage request from the generic path (1.4).
  - Fixed UFS bindings have unevaluatedProperties:false and do not declare the
    property (1.5); hence the real schema diagnostics (N1/F2/F3).
  - The board DTS carrying the property is a Huawei/vendor artifact; the value
    observed in ROUND27 is a logical DT value, not evidence of an enforced
    hardware voltage.

Decision tree:
  CASE 1 - pinned driver does not read it (THIS CASE, proven in 1.3):
    * Do NOT keep the property while calling it "effective": nothing in the
      pinned generic path consumes it, so that would be inaccurate.
    * Do NOT delete it merely to obtain a schema PASS: taskbook section 3
      forbids removing hardware properties to suppress diagnostics, and the
      property may document a vendor bootloader/PMIC contract we have not
      established.
    * Correct posture: classify it as UNRESOLVED vendor metadata. Before any
      change, collect evidence sufficient to decide which of these owns it:
        (i)   a pinned regulator/PMIC node constraint that actually enforces the
              VCC range (requires PMIC DTS + regulator consumer binding evidence
              for the exact rail, not inferred here);
        (ii)  a driver-side consumer that would need an explicit, reviewed
              extension to parse and apply the range (not present at fixed
              commit; adding it is a separate, reviewed code change);
        (iii) the original vendor DTS / vendor bootloader source showing the
              property's intended consumer and units;
        (iv)  board measurement / schematics tying the value to a real rail.
      Until one of (i)-(iv) is established with pinned evidence, the property
      stays as-is and the schema diagnostic stays reported. No fixed voltage,
      min/max number or PMIC parent-supply relation is proposed here.
  CASE 2 - if a pinned driver WERE found to read it (NOT this tree):
    * Only then would one pinpoint the exact read site, format and unit and let
      the binding describe that behavior. This case is explicitly not triggered.

Boundary restated: "driver doesn't parse it" is NOT equal to "hardware doesn't
need the range"; that hardware question remains OPEN and unanswered here.

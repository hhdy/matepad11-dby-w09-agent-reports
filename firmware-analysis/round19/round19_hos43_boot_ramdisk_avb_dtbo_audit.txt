Headline findings, each backed by a byte-level observation in the sections below:

1. Every one of the six boot-family containers carries a complete AVB footer whose
   original_image_size equals, byte for byte, the payload end computed independently
   from the boot header. Gap is 0 for five of them; dtbo.img has a 1694-byte
   page-alignment gap. No container is unsigned and none is truncated.

2. The stock ramdisk was NOT built from the same tree as the stock boot kernel.
   ramdisk.img's own build.prop declares Android 12 / SDK 31 / SKQ1.220804.001 and a
   build date of 2024-05-21, while boot.img's AVB properties declare Android 11 /
   patch level 2020-11. This is a deliberate HOS mix, not a mis-packed ramdisk.

3. ramdisk.img is not a conventional first-stage init ramdisk. It holds 17 CPIO
   entries: an AArch64 ELF /init (2 880 584 B), a 520-byte AVB public-key blob named
   patch_avb_key, a build.prop, and 13 empty directories. There is no fstab, no
   ueventd, no *.rc and no SELinux policy file in it.

4. The first-stage fstab therefore cannot come from the ramdisk. It is present in the
   stock base DTB at /firmware/android/fstab, together with /firmware/android/vbmeta
   whose parts list independently corroborates the AVB chain set decoded in section 5.

5. The stock base DTB has a /memory node whose reg is 0x0 0x0 0x0 0x0 - i.e. an empty
   placeholder that something outside the DTB must fill at runtime. Its /chosen node
   contains bootargs only and has no linux,uefi-system-table and no linux,uefi-mmap-*
   property.

6. None of the nine stock DTBO entries adds or changes /memory, /chosen,
   /reserved-memory or /firmware/android/fstab. Their only rootparam-adjacent action
   is fragment@142/143, which targets the base /rootparam node and writes five
   product-variant properties. The nine entries are nine hardware variants (VA..VI)
   of the same DBY-W09 board, distinguished by board-id, board_name and
   hardware_version.

7. Consequently, no stock DTBO in this firmware can explain a missing root /memory
   node and none of them can create the EFI-stub /chosen/linux,uefi-* handoff. That
   answer is bounded to the nine extracted entries and the paths actually inspected.

8. One genuine contradiction was found and is NOT explained away: the hashtree
   image_size values do not match the partition sizes measured independently. system,
   odm and cust are LARGER in AVB than in the LP metadata; vendor is smaller; and the
   five values sum to more than super.img. The values are internally consistent (all
   five tree_size fields reproduce exactly from image_size under a three-level
   dm-verity model), so this is a property of the stock package, not a parsing
   artefact. See 5.5a and UNKNOWN U-8.

5. WORK PACKAGE D - AVB FOOTER AND VBMETA DESCRIPTOR MAP
================================================================================

5.1 Tool situation

  No trusted AVB tool exists on this machine (ROUND12 reached the same conclusion and
  it was re-checked: avbtool not on PATH, no avbtool.py, no python avb module).
  Per the task's tool gate, a narrowly scoped read-only parser was written instead of
  installing anything. It is tools/avb_meta.py.

  Parser guarantees implemented:
   * reads byte arrays and files, never writes or patches an input;
   * every u32/u64 read is bounds-checked against the containing block;
   * footer original_image_size, vbmeta_offset and vbmeta_size are all validated
     against the real file size and against each other before use;
   * descriptor framing validates tag, body length, 8-byte alignment and that the
     walk ends exactly on the descriptor area boundary;
   * unknown descriptor tags are skipped by their declared length and reported by tag
     number, with the body deliberately not interpreted;
   * output is limited to descriptor type, target partition name, image_size and
     chain/parent relationship. No key bytes, key digests, salts, hash digests,
     signatures or rollback index values are emitted. The rollback index is only
     reported as "present / absent" for the vbmeta-level field, and per-descriptor
     rollback_index_location is reported because it is a slot address, not a secret.

5.2 Every vbmeta decoded, and the vendor layout anomaly that had to be resolved

  All 15 vbmeta blobs decode with identical structural rules:

  file                   auth  aux   desc_off desc_sz pk_off pk_sz desc+pk pad
  vbmeta.img              320  9280     0      8744    8744   520   9264   16
  vbmeta_cust.img         320   768     0       224     224   520    744   24
  vbmeta_hw_product.img   320   768     0       232     232   520    752   16
  vbmeta_odm.img          320   960     0       432     432   520    952    8
  vbmeta_system.img       320  1152     0       624     624   520   1144    8
  vbmeta_vendor.img       320  1152     0       616     616   520   1136   16
  recovery_vbmeta.img     320  3072     0      2504    2504   520   3024   48
  erecovery_vbmeta.img    320  3072     0      2504    2504   520   3024   48
  boot.img                320  1152     0       584     584   520   1104   48
  ramdisk.img             320   768     0       208     208   520    728   40
  dtbo.img                320   896     0       336     336   520    856   40
  recovery.img            320   768     0       208     208   520    728   40
  erecovery.img           320   768     0       208     208   520    728   40
  recovery_ramdisk.img    320   768     0       216     216   520    736   32
  erecovery_ramdisk.img   320   768     0       216     216   520    736   32

  The invariant across all 15 is: public_key_offset == descriptors_size and
  descriptors_size + public_key_size + pad == auxiliary_data_block_size.
  In other words this firmware places the public key inside the AUX block immediately
  after the descriptor array, not inside the authentication block as a stock AOSP
  avbtool would. A naive AOSP-shaped reader therefore reports
  "public_key exceeds auth size 320" on every image here. That is a layout difference,
  not corruption: the arithmetic closes exactly on all 15 blobs with 8..48 bytes of
  zero padding, and the release string in each header reads "avbtool 1.1.0" (except
  vbmeta_cust.img, which reads "avbtool 1.2.0").

  Consequence for the reader: both the hash and hashtree descriptor bodies in this
  firmware also differ from the AOSP reference layout (a fixed 32-byte
  hash_algorithm array with trailing NUL-terminated strings and a 64-byte reserved
  area). The parser accepts a descriptor only if the declared field triplet plus the
  string block plus zero padding exactly fills the declared body length, and it tries
  the AOSP layout as a fallback. All 15 blobs resolved uniquely under that rule.

  marked PRELIMINARY. Three independent quantities nevertheless agree with the
  decoded values, which is why the confidence is high:

  a) footer.original_image_size equals the payload end computed purely from the boot
     header for boot.img, ramdisk.img, recovery.img, recovery_ramdisk.img and
     dtbo.img - five independent arithmetic chains, gap 0 in every case.
  b) the hash descriptor image_size for dtbo equals the DTBO table header's own
     total_size (2 963 810), a field read by a different code path in ROUND2/3.
  c) the stock base DTB's /firmware/android/vbmeta node lists, in text, the set of
     partitions AVB is expected to cover:

5.5a DISAGREEMENT between the AVB hashtree image_size and the measured partition size

  This must be stated plainly rather than smoothed over. The hashtree image_size does
  not match the partition sizes measured independently:

    partition    AVB hashtree image_size   measured partition size          source
    vendor              947 318 784       1 022 038 016   ROUND4 odm/vendor extraction
    odm                 635 641 856          51 593 216   ROUND4 extraction
    system            3 525 328 896       3 206 561 792   ROUND3 LP metadata (slot0)
    cust                 90 726 400           8 024 064   ROUND3 LP metadata (slot0)
    hw_product        2 369 454 080       2 826 309 632   ROUND3 LP metadata (slot0)

  For vendor the AVB figure is smaller than the partition (plausible if a filesystem
  image smaller than its container was signed). For odm, cust and system the AVB
  figure is LARGER than the partition it names, which cannot be explained by that
  mechanism. A direct byte search for the measured sizes inside the corresponding
  vbmeta images found no big-endian and no little-endian occurrence of those values,
  so the disagreement is not a field-offset mistake on one side - the two numbers
  simply are not both present.

  The sum of the five hashtree image sizes (7 568 470 016 B) also exceeds super.img
  (7 114 729 004 B), whereas the five LP partition sizes sum to 7 114 526 720 B, i.e.
  super.img minus 202 284 bytes of metadata. The LP side is therefore internally
  consistent and the AVB side is not reconcilable with it from offline evidence alone.

  This is recorded as UNKNOWN U-8, not resolved and not explained away. It matters
  for any future packaging attempt: it means the AVB hashtree descriptors in this
  stock package cannot be used as a statement of partition geometry.

5.6 What this work package does NOT establish

  No signature verification was attempted. No AVB policy was bypassed or altered. The
  descriptor contents prove coverage claims; they do not prove that a device would
  accept a modified image, and they do not reveal any key material.

6. WORK PACKAGE E - NINE DTBO ENTRIES, MEMORY / EFI / CHOSEN / ROOTPARAM
================================================================================

6.1 Method

  The nine dtbo_entry_N.dtbo files already extracted by ROUND3 were decompiled with
  dtc 1.7.0 into .dts text in the ROUND19 temp directory; the firmware was not
  re-extracted. The four base FDT candidates from ROUND3 (boot_fdt_candidate_0..3)
  were decompiled the same way. For each entry the audit records root identity,
  fragment count, whether target-path is used, the full __fixups__ symbol list, and
  the content of the fragment that targets the base /rootparam node.

6.2 The base DTB baseline (what the overlays are overlaying onto)

  /memory:
      device_type = "memory"
      reg = <0x00 0x00 0x00 0x00>          <- all-zero placeholder
  /rootparam:
      phandle only, no properties          <- an empty node waiting to be filled
  /chosen:
      bootargs = "rcupdate.rcu_expedited=1 rcu_nocbs=0-7 kpti=off"
      (no linux,uefi-system-table, no linux,uefi-mmap-start/size/desc-size/desc-ver)
  /firmware/android/vbmeta:
      parts and ta_parts lists (quoted in 5.4c)
  /firmware/android/fstab:
      system, vendor, odm entries, each in an ext4 and an erofs flavour, all with
      fsmgr_flags = "wait,logical,avb"

  The /memory reg being zero is the direct answer to the task's "missing root /memory
  node" question in its true form: the node is present but carries no usable range.

8. REMAINING UNKNOWNS AND THE EXACT EVIDENCE EACH WOULD NEED
================================================================================

U-1  Whether the base DTB's /memory node is filled by ABL/UEFI at runtime, and with
     what range.
     Needed: an ABL/UEFI artefact plus either a runtime FDT dump from a device session
     or a documented memory-map handoff in that artefact. Offline DTB and DTBO
     evidence in this package cannot answer it; the placeholder is all zeros.

U-2  Whether the EFI-stub /chosen/linux,uefi-* handoff is produced at runtime by
     something other than DTB/DTBO.
     Needed: the same artefact as U-1, or a runtime /proc/device-tree/chosen dump.
     Note the stock /chosen contains bootargs only, so if the handoff exists it is
     added after the DTB stage.

U-3  Whether HOS's ABL consumes the os_version field of the standalone ramdisk
     container, given ramdisk.img says Android 12 while boot.img says Android 11.
     Needed: ABL behaviour evidence, or a boot log showing the ramdisk container being
     accepted. The discrepancy itself is proven; its consequence is not.

U-4  Whether chain validation for the erecovery slot tolerates an embedded vbmeta that
     declares partition name "recovery" (because erecovery.img is byte-identical to
     recovery.img and therefore carries recovery's vbmeta verbatim).
     Needed: AVB log output from a device, or the erecovery boot code path.

U-5  The purpose of /patch_avb_key in the stock ramdisk.
     Needed: the consumer of that file (a vendor tool or a boot-time code path). Its
     structure (2048-bit AVB public key blob, 520 B) is proven; its use is not.

U-6  Whether the 1694-byte gap between dtbo.img's payload end and its vbmeta block is
     consumed by anything. It is all-zero padding to the next 4096 boundary, which is
     the expected alignment behaviour, but nothing proves a consumer ignores it.

U-7  The exact reserved-field widths inside this vendor's hash/hashtree descriptors.
     The parser derives field placement from an exact-fill and tail-all-zero rule and
     the result closes on all 15 blobs, but the field names are AOSP names applied to
     a vendor layout. This is the one place where the parser, not the data, could be
     wrong in naming.

U-8  What the hashtree image_size values actually denote, given that they disagree with
     the measured partition sizes (section 5.5a): larger than the LP partition for
     system, odm and cust, smaller for vendor, and summing to more than super.img.
     Needed: either a stock super.img layout dump produced by the vendor's own
     packaging tool, or the original partition images as signed (before any super
     assembly), or a device-side avb/verity log showing the accepted image_size.
     This is the single largest open item in this round because it blocks any attempt
     to reconstruct a bootable stock layout from AVB metadata.

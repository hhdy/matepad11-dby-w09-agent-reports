3. 锁定 draft 无法 apply 的根因（可复现）
--------------------------------------------------------------------------------
3.1 现象（在精确 ACK checkout、工作树干净、源 blob 一致的前提下）

  git apply --check --verbose <pinned draft>
    Checking patch drivers/phy/qualcomm/phy-qcom-qmp-ufs.c...
    error: while searching for:
    #include <linux/phy/phy.h>
    #include <linux/platform_device.h>
    #include <linux/regulator/consumer.h>
    #include <linux/reset.h>
    #include <linux/slab.h>
    error: patch failed: drivers/phy/qualcomm/phy-qcom-qmp-ufs.c:16
    error: drivers/phy/qualcomm/phy-qcom-qmp-ufs.c: patch does not apply
    DRAFT_CHECK_RC=1

  patch -p1 --dry-run:  Hunk #1 FAILED at 16.  1 out of 5 hunks FAILED
  （同一 patch 的其余 4 个源码 hunk 可应用）

3.2 排除性验证
  - 文件内容不是原因：`git rev-parse HEAD:drivers/phy/qualcomm/phy-qcom-qmp-ufs.c`
    = 8af777f7… = patch 头声明的源 blob；逐字节比较 hunk 的 5 行上下文与文件 16–20 行，
    结果完全相同（含行尾，无 CR、无尾随空格）。
  - 不是空白策略：`--ignore-whitespace` 仍失败；`--recount` 仍失败。
  - 不是位置偏移：`git apply --check -C1` 与 `-C0` 均 rc=0。

3.3 根因（最小复现）
  该 patch 的首个 hunk 形如：
      @@ -16,5 +16,6 @@
       <5 行 include 上下文>
      +#include <linux/string.h>
      （hunk 到此结束，之后直接是下一个 @@）
  即"以新增行结尾、且没有尾随上下文"。对同一 6 行内容做对照实验：
      A 组（无尾随上下文）→ git apply 失败、patch(1) 失败
      B 组（补一行尾随空行，@@ -15,7 +15,8 @@）→ git apply 通过
  结论：失败来自 hunk 尾部上下文不足，与 ACK 版本、文件内容无关。
  这与 2号 AI 在 round63-ufs-phy-integration.md §9 记录的 hosted run 45441391557
  结论一致（"insufficient include-block context … its later four source hunks applied
  cleanly"），本轮以本地最小实验独立复现并补上了对照证明。

5. 独立代码逻辑复核（任务书 §2.5 / §2.6 / §2.7）
--------------------------------------------------------------------------------
以下结论基于应用后的实际源码（ack-6.18.33-a30/common），不是对 patch 文本的转述。

5.1 property 缺省路径完全保持原状
  qmp_ufs_regulators_enable(): `if (!qmp->vdda_phy_always_on) return regulator_bulk_enable(num_vregs, vregs);`
  qmp_ufs_regulators_disable(): 对应 `regulator_bulk_disable(num_vregs, vregs)`
  → 未配置该属性的节点，enable/disable 与上游实现逐语句等价（无额外 set_load、无额外引用）。

5.2 首次 power-on 只取一个 vdda-phy enable 引用，并恢复 init_load_uA
  顺序：regulator_set_load(vregs[0], vregs[0].init_load_uA) → 若 !vdda_phy_enabled 则
  regulator_enable(vregs[0]) 并置 vdda_phy_enabled=true → regulator_bulk_enable(num_vregs-1, &vregs[1])
  → vdda-phy 单独处理，其余 rail 仍走 bulk helper。

5.3 power-off：其余 rail 正常 disable，vdda-phy 保留 enable、load 归零
  regulator_bulk_disable(num_vregs-1, &vregs[1]) → 若曾 enable 过则 regulator_set_load(vregs[0], 0)，
  不调用 regulator_disable(vregs[0])。即 enable 引用保留、负载投票撤销，符合 always-on 语义。

5.4 后续 power-on 恢复 load、不重复 enable
  `if (!qmp->vdda_phy_enabled)` 保护使第二次及以后不再 regulator_enable；
  set_load(init_load_uA) 每次都会重新投票（幂等）。

5.5 devm 清理顺序正确
  qmp_ufs_probe() 内实际顺序（行号为应用后文件）：
    23  devm_regulator_bulk_get_const(...)   ← 先取得受管 bulk handle
    39  of_property_read_bool(np, "vdda-phy-always-on")
    48  devm_add_action_or_reset(dev, qmp_ufs_vdda_phy_cleanup, qmp)  ← 后注册
    54  qmp_ufs_register_clocks()
    58  devm_phy_create()
  devres 采用 LIFO：后注册的 cleanup 先执行，因此 cleanup 一定在 bulk regulator handle
  释放之前运行，能安全访问 vregs[0].consumer。
  注册时 vdda_phy_enabled 为 false，`_or_reset` 的即时回滚调用为 no-op，不会误 disable。

5.6 状态位只有一个写入闭环（程序化核对写入点）
  vdda_phy_enabled: 仅 1877 置 true（regulator_enable 成功之后）、1851 置 false（cleanup 内），
  无其他写入点 → 不存在重复 enable 或遗忘平衡的路径。

5.7 错误路径不留未平衡 enable/load
  power_on 的 clk 使能失败 → err_disable_regulators → qmp_ufs_regulators_disable()：
  其余 rail 撤销、vdda-phy load 归零，但保留 enable（这是 always-on 的稳态，由 §5.5 的
  cleanup 最终平衡）。regulators_enable 内部失败路径 err_clear_load 亦把 load 归零。
  → 失败后不存在"load 已投票但无人撤销"或"enable 计数多记一次"的情形。

5.8 拒绝不符合 vdda-phy 首位约束的 regulator list
  enable/disable 两个 helper 与 probe 三处都校验
  `cfg->num_vregs < 2 || strcmp(cfg->vreg_list[0].supply, "vdda-phy")` → 返回 -EINVAL
  （probe 处直接 goto err_node_put），不会把特殊处理套用到错误的 rail 上。

5.9 pinned ACK 的 QMP UFS regulator 列表核对（程序化解析）
  在 blob 8af777f7 的源文件中解析全部 `static const struct regulator_bulk_data *[]`：
    LISTS_TOTAL=15，LISTS_OK=15，LISTS_ORDER_VIOLATIONS=0
  15 组全部恰为 2 项且顺序为 ['vdda-phy', 'vdda-pll']

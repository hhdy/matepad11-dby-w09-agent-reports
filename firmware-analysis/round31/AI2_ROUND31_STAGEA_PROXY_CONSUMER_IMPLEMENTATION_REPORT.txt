2. TOPOLOGY SEMANTICS PROVEN BEFORE IMPLEMENTATION
--------------------------------------------------------------------------------
Decision question of this round: where does `proxy-supply` live, and which
of_node does regulator_get() consult?

  (a) ACK's qcom-rpmh-regulator registers ONE platform device per PMIC group
      node (e.g. rpmh-regulator-ldoa5-style group nodes under
      /soc/rsc@18200000); every child regulator shares that one `dev`.
      Verified in probe: the child loop calls devm_regulator_register with
      the same parent dev for every regulator_bulk entry of the group.
  (b) The regulator core's registration hook sees
      (dev = GROUP device, config->of_node = CHILD node).
  (c) Therefore `proxy-supply` on the group node and `qcom,proxy-consumer-*`
      on child nodes is the DESIGNED shape, matching ROUND13's stock-DTS
      reading; a naive "self-reference" reading (proxy-supply pointing at the
      child that carries the consumer flags) is wrong for the core hook and
      is NOT what the stock DTS does.
  (d) Resolution at helper time: regulator_get(dev, "proxy") →
      of_parse_phandle(dev->of_node, "proxy-supply", 0) → the child node
      registered moments earlier in the same probe → rdev found by
      class_find_device_by_of_node over the regulator_class list. In-register
      lookup during probe works because device_register + class list add
      happen inside regulator_register() before the helper runs.
  (e) Whole-PM8150-as-one-device consequence: there is at most ONE
      proxy-supply per PMIC group device, so multiple children of the same
      group necessarily SHARE one proxy consumer object. The schema cannot
      reject that shape (both children are individually schema-valid); it is
      recorded as a designed, documented property of this port instead.

3. SEMANTIC CORRECTION APPLIED: NO sync_state ON THIS ACK
--------------------------------------------------------------------------------
The KONA-lineage file carries an optional revoke path keyed on device sync
state (fw_devlink sync_state). The pinned ACK 8ad08f75 has NO regulator-side
sync_state support (zero hits for sync_state in qcom-rpmh-regulator.c and
core.c). The port therefore uses the classic teardown only:

      late_initcall_sync(regulator_proxy_consumer_remove_all)

dropping every outstanding vote exactly once when all built-in drivers have
had their probe chance, and making removal permanent
(regulator_proxy_consumer_register after removal returns -EPERM). This
matches the pinned ACK's actual capabilities rather than transplanting a
mechanism whose trigger would never fire here.

Lifecycle semantics implemented (identical to the KONA file where the pinned
ACK can support it):
  register:  per child with qcom,proxy-consumer-* — one regulator_get, one
             regulator_enable, one regulator_set_load(init load), optional
             voltage range applied via regulator_set_voltage on registration
             flags; state recorded on the rdev.
  unregister: reverse in one shot — disable once, drop load vote to 0, put;
             idempotent and NULL-safe.
  remove_all (late_initcall_sync): walks the list once, permanent shutdown;
             later registrations refused with -EPERM.
  error paths: every allocation/get failure unwinds what was taken before
             returning; the unit test asserts no leaked votes.

5. REAL BUILD ERROR FOUND AND FIXED
--------------------------------------------------------------------------------
The first //common:dby_w09 build FAILED. Root cause: a local variable declared
as `u32 current` inside proxy-consumer.c collided with the kernel-wide
`current` macro (current = get_current(), type struct task_struct *), which
clang rejects at the point of use. Fixed by renaming the variable to `ua`;
no other error existed. The failing build log was overwritten by the rerun in
the working log file (only the final PASS log is retained), so the exact
clang diagnostic text is reported by kind, not verbatim; the fix is visible
in the patch content (no `current` identifier remains, verified by grep).

This is a faithful example of the taskbook's premise: checks alone did not
catch it — only the real build did.

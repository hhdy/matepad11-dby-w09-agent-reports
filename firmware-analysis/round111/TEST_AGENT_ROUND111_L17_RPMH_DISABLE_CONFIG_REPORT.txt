0. 结论摘要
--------------------------------------------------------------------------------

A. `qcom,always-wait-for-ack`：三个 base 候选的 **L17 child 自身均为 ABSENT**，
   L17 group 也是 ABSENT；更关键的是——**整个 base 设备树里此属性出现 0 次**
   （3471/3471/3433 个节点、1753/1753/1752 个 label 全覆盖扫描）。
   九个 stock DTBO 同样 **0 处** 声明该属性。因此 L17 的 disable 路径不会进入
   `rpmh_write()` 同步分支，仍走 `rpmh_write_async()`（见 §9）。

B. Coupling：`regulator-coupled-with` / `-max-spread` / `-min-spread` /
   `-no-balance` 在三个 base、九个 DTBO 中均为 **0 实例**。
   HOS vendor 侧也不存在 coupling-like 属性（按 `coup|spread|balance` 子串全树扫描，
   命中 0 条）。反向耦合扫描：**不存在任何属性以 phandle 形式指向 L17 child**
   —— supply 类引用 0 条，非 supply 类数值巧合 0 条（见 §5）。

C. Parent supply：L17 group 与 L17 child 上 **没有任何 `*-supply` / `*-parent-supply`
   属性**；`vdd-l13-l16-l17-supply`、`vin-supply`、`vph-pwr-supply` 在整个 base 中
   出现 0 次。这必须与 ACK 驱动行为区分开：驱动从**静态表**取得 `supply_name`
   = `vdd-l13-l16-l17`（不由 FDT 决定），core 随后按该名字做 DT lookup，失败后在
   `have_full_constraints()` 为真（本机 DT 已填充，故恒为真）时绑定 **dummy regulator**。
   所以准确表述是"FDT 未声明父供电"，而不是"该 regulator 在 core 里没有父级"（§6）。

D. Vendor proxy：L17 group **没有** `proxy-supply`。同子树内 5 个 group
   （ldoa5 / ldoa9 / ldoa14 / ldoc11 / cxlvl / mmcxlvl）确实带 `proxy-supply` 且各自指向
   自己的 child——这正好构成对照：L5（ROUND106）有 proxy，**L17 没有**。
   因此不存在"把 L17 的 proxy 误读成物理输入"的风险，本报告也不做任何电气输入断言。

E. DTBO 覆盖：九个 entry **全部**不修改 L17 group / L17 child。逐 entry 的 fragment
   target 100% 解析成功（143–145 个 fragment/entry，unresolved 0、dangling 0），
   **没有任何 fragment 落在 `/soc/rsc@18200000` 子树内**。九个 entry 里唯一涉及 L17 的
   是 `/fragment@64`（target label `ufshc_mem`）新增的 **consumer 侧** `vcc-supply`，
   其 fixup 指向 label `pm8150_l17`——即 UFS host 消费 L17，而不是改 L17。

F. Failure-boundary：L17 静态配置对应 **异步 `rpmh_write_async()`**。
   依据是 ACK 驱动的分支条件本身，不是 regulator 类型推断（§9 给出源码行号）。

G. 未关闭项：本报告不涉及运行时电压/使能状态、PMIC ACK 实际完成状态、ABL 实际选中的
   DTBO entry、电气原理图结论。全部保持独立、未因此次取证而"关闭"。

  同理，`supply_name` 是 C 字符串 lookup key，**不能**作为实际物理供电网的证据。

9.2 判定
  对 L17：
    enable  → 同步 rpmh_write()
    set_mode→ 同步 rpmh_write()（与属性无关，恒为 true）
    disable → **异步 rpmh_write_async()**
  因为 L17 child 上没有 `qcom,always-wait-for-ack`（§3.1），
  `always_wait_for_ack` 保持 false，disable 的 `wait_for_ack=false` 不会升级为同步。

  因此本轮静态配置的 failure boundary 属于 **异步** 一侧：
  `regulator_disable()` 的返回值只反映"命令是否成功排队/写入"，**不反映 PMIC 是否已
  完成 ACK**。`rpmh_write()` 的 `-ETIMEDOUT` 分支在本配置下不会被 L17 disable 触发。

9.3 与 ROUND90 的关系（不重复推导，只做边界说明）
  ROUND90 已确认 load-zero-before-disable 可避免 core 在 enable_count 递减后执行
  非零 load 的 DRMS 更新。本轮只补充"该路径的错误返回语义是异步"这一静态事实；
  两者不矛盾，也不构成运行时结论。

5. KNOWN LIMITATION RETAINED (C8) — stated explicitly, NOT solved by this patch
--------------------------------------------------------------------------------
If regulator_disable() genuinely FAILS after this patch:
  * ufshcd_config_vreg(dev, vreg, false) has ALREADY succeeded, i.e. the load
    was cleared while the consumer enable reference is still held at the
    driver level (vreg->enabled stays true, ret != 0, dev_err logged).
  * Per the patch's own comment, the ACK regulator core may decrement the
    consumer enable_count inside regulator_disable() BEFORE running a
    fallible DRMS update — so a failed disable leaves ambiguous reference
    accounting: the driver cannot safely retry regulator_disable() (risk of
    over-decrement) and cannot detect whether the reference was actually
    dropped. regulator_put()/managed-put semantics cannot repair that state.
  * What the patch DOES add for this path: the next ufshcd_enable_vreg()
    restores the active load even when vreg->enabled is still true (C5), so
    the load ordering is repaired; the ENABLE-REFERENCE bookkeeping problem
    is NOT repaired. This limitation pre-exists (the old code had the same
    ambiguity, plus a lost-load window); this patch narrows it but does not
    claim to solve it. No error-path regression was introduced: the disable
    failure path returns the regulator_disable() error unchanged and performs
    no additional put.

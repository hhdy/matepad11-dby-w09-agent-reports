6.5 dtschema 2023.9 对照复跑

  环境：<副本>/round18-venv-2023，dtschema 2023.9 / jsonschema 4.17.3 / Python 3.12.3
        （pip install "dtschema==2023.9"，实测安装成功并记录版本）
  做法：先 git clean -fdx 清除 DT 中间产物，用 2023.9 重新生成 processed-schema.json，
        再跑 dt_binding_check、dt-doc-validate、dt-validate 与 15 个 fixtures。

     4 个 example 全部 DTEX + DTC [C]，无 validation diagnostics。

       .../bindings/firmware/gunyah-cma-mem.yaml

     schema 与其 example 的编译与校验。

  重要工具差异（本轮实测，直接影响判定方法）：
    2023.9 的 `-l/--limit` 语义是"limit validation to schemas with $id matching
    LIMIT **substring**"，只接受一个子串，不接受冒号分隔的 schema 列表；
    2026.9 的 `-l` 接受冒号分隔的 schema 路径列表。
    若把 4 个 schema 的冒号串直接喂给 2023.9，$id 匹配不到任何 schema，结果是
    **不做任何校验、静默成功**：首轮实测 8 个负例全部被误判为 ACCEPT
    （u03/u03b/u04/u05/u06/u07/u08 与 p04），MISMATCH_COUNT=8。

    结论：跨 dtschema 版本比对时不得假定 -l 语义一致；判定必须以内核自身的
    调用形态（-u -p）为准，这也是本轮最终的权威口径。

  为消除版本变量，2026.9 侧同样补跑了内核形态（强制删除并用 2026.9 重建
  processed-schema.json，避免沿用 2023.9 生成的旧格式）：
    dt_binding_check RC=0；4 个 example diagnostics=0；
    MISMATCH_COUNT_2026_9_KERNELFORM=0（15/15）

           确保 4 个 example DTB 全部重新 DTEX/DTC 生成。

  F7 dt-validate 恒 exit 0（工具层缺陷，影响判定方法）
     现象：诊断已打印（is too short / is too long）但进程返回 0。
     根因：dtschema 2026.9 的 dt-validate main() 无 return 语句，sys.exit(main())
           收到 None 即 0；这正是内核 scripts/Makefile.dtbs 中
           "dt-validate ... || true" 会彻底吞掉真实失败的机制。
     处置：fixtures 判定改为"是否输出非空 diagnostics"，不使用 $?；直接调用
           时同时记录 rc 与 diagnostics 行数。

  F8 dtschema 2023.9 的 -l 语义与 2026.9 不同，导致首轮对照出现 8 个假 ACCEPT
     现象：把 4 个 schema 的冒号串传给 2023.9 的 -l 后，所有负例（u03/u03b/u04/
           u05/u06/u07/u08、p04）全部被判 ACCEPT，MISMATCH=8。
     根因：2023.9 的 -l 是"按 $id 子串匹配"，只接受单个子串；冒号串匹配不到任何
           $id → 实际不校验任何 schema → 静默成功（rc 仍为 0）。
     处置：改用内核真实形态 dt-validate -u <bd> -p <schema> <dtb>，2023.9 侧
           MISMATCH=0（15/15）；并在 2026.9 侧同样补做内核形态（MISMATCH=0）。
     结论：跨版本比对不得假定 -l 语义一致；"-l 生效但没匹配到"与"校验通过"
           在输出上完全一样，是最容易造成假 PASS 的陷阱之一。

  F9 processed-schema.json 跨版本残留导致 2026.9 抛异常
     现象：先用 2023.9 生成 processed-schema.json 后，切回 2026.9 直接校验，
           正例全部抛 Exception 并返回非 0：
             Processed schema out of date, delete and retry: .../processed-schema.json
           此时若只看"负例仍 REJECT"会误以为结果正常。
     根因：两个 dtschema 版本的 processed schema 二进制格式不兼容，且内核 Makefile
           的 .cmd 依赖判定认为无需重建。
     处置：rm -f processed-schema.json .processed-schema.json.cmd 后强制用目标
           版本重建，再跑校验（最终 2026.9 形态 sha256 447e4c45…）。

10.2 需要交叉验证的工具层/产物层事实（供二号 AI 对照）

  C1 dtschema 的 maxItems→minItems 推导
     只写 maxItems 而无 minItems 时，minItems 被推导为等于 maxItems（精确长度）。
     这既解释了 UFS example "power-domains is too short" 的根因，也解释了
     ROUND57 在固定八项 items 列表上再加 minItems/maxItems 触发 meta-schema
     不兼容的现象。本轮修法：显式 minItems: 1（shared + SM8250 then 两处）。
     决定性证据：加上后 example 与 15 个 fixtures 全部符合预期，无需删除
     example、无需放宽 unevaluatedProperties。

  C2 dt-validate 恒 exit 0（见 F7）
     任何以"make dt_binding_check 返回 0"为依据的 PASS 结论都不可靠。

  C3 $ref 失败后的 diagnostics 级联
     子 schema（$ref 目标）校验失败时不再产生 annotation，导出 schema 的
     unevaluatedProperties: false 会把 common 中已定义的属性全部判为
     unexpected。因此"Unevaluated properties are not allowed (...)"通常是
     次生报告，应优先修 $ref 目标的真实失败。

  C4 二号 AI 分支状态与 artifact 缺陷（只读观察）
     分支 HEAD 已到 1db78203bd044993e3db63eb86ad79a9d2eba728（快照为 faae6c04）。
     round36-corrected-power-domain-range.patch 当前 blob f36f13e8 在 hunk 之间
     含一个空行 → git apply 无法解析（GNU patch 可）。建议其侧删除该空行。
     round63-0001 补丁 hunk 1 缺尾随上下文 → 默认上下文 git apply 失败；
     其 driver 代码续行对齐也会被判 CHECK。本轮的 09f581f4 是可用形态。

  C5 dt-validate 的 -l 参数在不同 dtschema 版本语义不同（见 F8）
     2023.9：单个 $id 子串；2026.9：冒号分隔的 schema 路径列表。
     用错形态会得到"零 diagnostics 的假 PASS"。建议双方在 schema 结论中明确
     写出使用的 dt-validate 形态与 dtschema 版本。

4. WORK PACKAGE D — compare with exact ACK 6.18.33 facts
----------------------------------------------------------------------
Status: PASS (classification only; no ACK source re-read, no build.)

ACK facts compared (exactly the four supplied by the task):
  ACK-1: SM8250 RPMHPD selects plain MMCX with NO MX parent.
  ACK-2: CX uses CX-with-MX-parent.
  ACK-3: other SoC tables select MMCX-with-CX-parent, not MX.
  ACK-4: generic GenPD parent propagation passes the same pstate absent a
         required-opps translation table (ROUND22 also confirmed rev2 carries
         only 1 power-domain on the UFS host pre-rev2; not re-measured here).

Observation: HOS4.3's MMCX provider DOES carry explicit MMCX->MX parent edges
(EDGE 1 ALL and EDGE 2 AO, A.3), and the MX provider additionally carries a raw
->CX parent-supply property (A.2). The HOS MMCX ALL child init corner is 0x40
while its MX parent-target children use 0x10, with a stored max-u32 dropout
value on the MMCX side. So the HOS parent state is NOT a same-value copy of the
child corner; the two providers use different corner spaces.

Classification of "a simple MMCX->MX parent descriptor" in ACK:
  - As same-state propagation: ACK-4 means adding only a parent phandle, with
    no required-opps translation, would pass the SAME pstate to MX. That is
    structurally different from the HOS MMCX(0x40)/MX(0x10) corner relationship
    observed above -> NOT equivalent to HOS semantics.
  - As requiring explicit corner translation: YES. Reproducing HOS dropout
    delta would need an explicit corner translation table (required-opps or
    equivalent) plus a documented encoding for 0xffffffff dropout. That
    encoding/rule is NOT_CAPTURED (C.2/C.3), so the translation cannot be
    derived from available evidence.
  - Overall: UNRESOLVED for implementation. A bare parent descriptor is
    insufficient; an explicit, evidence-backed translation rule does not yet
    exist locally. This is design evidence only — no descriptor was written.

D-2  checkpatch --strict 退出码为 1（3 条 CHECK，0 errors / 0 warnings）
     任务书 §7 的硬性要求是「0 errors、0 warnings」，已满足；未要求退出码为 0。
     但 --strict 会把 CHECK 计为非零退出，因此若审查方以「退出码必须为 0」为判据，
     本项应改判为「静态检查不干净」，总判定随之降为 FAIL。本报告不替审查方做这个选择，
     只把事实摆全：3 条 CHECK、文件名、行号、原文均在 §9 与 checkpatch 日志里。
     注：本轮**没有**修掉这 3 条 CHECK——任务书禁止修改补丁，测试方无代码修改权。

D-3  独立 SPDX 检查器 NOT RUN
     scripts/spdxcheck.py 需要 python3-ply，本机未安装（ModuleNotFoundError）。
     未安装依赖（会改变环境，超出授权），如实标注 NOT RUN。

D-4  GNU patch dry-run 与 git apply 结果分歧（已确认不影响判定）
     为给出「零 fuzz / 零 offset」的第二个视角，对每个补丁额外跑了一次
     `patch -p1 --dry-run --fuzz=0`。结果 8/17 个补丁被 GNU patch 报
     "Hunk #N FAILED"，而同一字节的补丁在 git apply 下 --check 与 apply 均成功，
     且最终内容树精确等于声明的基线 tree 77e2b2b1…。
     结论：这是 GNU patch 的定位/状态启发式差异（它在 dry-run 中对同一文件的多个
     hunk 采用自身的位置推算），不是补丁漂移。因此本报告**不以 GNU patch 输出作为
     fuzz/offset 判据**，而以「git apply 无 fuzz/offset 机制 + 内容树哈希一致」为准；
     两种输出都原样留在 apply-check 日志里供审查。

  - host 回归是 mock 头文件的宿主测试，不是设备/真实 regulator core 运行。
  - 设备侧、固件侧、刷机侧全部未触碰，本轮无相关证据。

§12 工具语义说明（两处容易被误读的地方）
--------------------------------------------------------------------------------
[12.1] 为什么「git apply 成功」就等于「零 fuzz、零 offset」
  git apply 不做模糊匹配：hunk 的上下文必须逐字节命中，否则直接失败；它也不做
  「按偏移去找相近位置」的尝试。因此 17/17 与 seam-v2 均 --check 通过并 apply 成功，
  在机制上即排除 fuzz 与 offset。更强的证据是内容树哈希：17 补丁重放后两棵树都得到
  77e2b2b1…，与 SOURCE_NOTE 声明的补丁基线 tree 完全一致——这比任何 fuzz 计数都硬。

[12.2] KTAP 的 `# module:` 行不是「被编译成模块」
  见 §6 末尾：该行是属性行，值取自 KBUILD_MODNAME，复合对象名带 -test 后缀就会打印。
  真正的判据是 CONFIG...=m（0 处）与 *.ko（0 个）。

[12.3] 与 ROUND35S 的关系（只作历史参照，不作为本轮证据）
  ROUND35S 的 seam 是 16804 B / 7 files / +399-1；本轮 seam-v2 是 16797 B / 7 files /
  +399-1，路径集合相同、变更量相同、体积差 7 字节，与「只把 tristate 改成 bool 并调整
  help 说明」的声明自洽。但本轮全部结论均来自对 1fbc32a3… 这一份字节的独立执行，
  未引用 ROUND35S 的任何 PASS。

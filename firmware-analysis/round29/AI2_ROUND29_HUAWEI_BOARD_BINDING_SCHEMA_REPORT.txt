2.5 Why the ROUND28 v3 draft could not resolve F1, and what -l really selects
  ROUND28 v3 was run as (quoted from the ROUND28 report, section 3.3):

      dt-validate -s <v3 schema json> -l 'huawei,dby-w09' <composite.dtb>

  dt-validate --help, verbatim:
      -l LIMIT, --limit LIMIT
                        limit validation to schemas with $id matching LIMIT
                        substring. Multiple substrings separated by ':' can be
                        listed (e.g. foo:bar:baz).

  With -l 'huawei,dby-w09', every schema whose $id does not contain that substring
  is dropped by _filter_match() before validation (validator.py 462-468, and the
  filter is applied to compat_map selection at 475 and to always_schemas at 485).
  arm/qcom.yaml does not contain 'huawei,dby-w09' in its $id, so it was never
  loaded into the run. F1 could therefore neither be observed nor fixed by that
  command - the run only ever evaluated the draft against /rootparam.

  The v3 top-level `additionalProperties: true` cannot compensate: that key governs
  how the DRAFT evaluates the node it is applied to. F1 is emitted by a different
  schema (arm/qcom.yaml) which the -l filter had removed. The flag was also exactly
  what ROUND29 section 5 forbids, so v3 is correctly not treated as mergeable.

3.2 Scheme 2 - an independent Huawei board binding, joined to root selection
  Two joining mechanisms exist in the fixed validator; both were built and tested.

  2a) declare properties.compatible (the "ordinary board binding" shape):
        properties:
          $nodename: { const: '/' }
          compatible:
            items:
              - const: huawei,dby-w09
              - const: qcom,sm8250
        additionalProperties: true
      dt-doc-validate RC=0. But because the schema then contains
      properties.compatible, it is registered in compat_map under huawei,dby-w09
      (validator.py 418-428) and, being the FIRST compatible string of the node,
      it wins the first-match loop and `break`s (validator.py 470-479). arm/qcom.yaml
      is then never applied to the root node at all. F1 disappears by precedence,
      not by resolution. The fixed validator also emits a hard warning:
        Warning: Duplicate compatible "qcom,sm8250" found in schemas matching "$id":
            http://devicetree.org/schemas/arm/huawei,dby-w09.yaml
            http://devicetree.org/schemas/arm/qcom.yaml#
      => rejected: it hides the diagnostic instead of resolving it, which is
         exactly what ROUND29 section 6.6/5 forbids.

  2b) use a `select` key instead of properties.compatible (so the schema lands in
      always_schemas and does not shadow anything):
        select:
          properties: { $nodename: { const: '/' } }
          required: [ compatible ]
          allOf:
            - properties: { compatible: { contains: { const: huawei,dby-w09 } } }
      dt-doc-validate RC=0, and F1 is untouched because qcom.yaml is still applied
      (proved in 4.3 canary). => cannot be the sole solution; at most a supplement.

3.4 Chosen architecture: Scheme 1, plus a node-name-keyed schema for /rootparam
  /rootparam has no compatible property and none may be fabricated. In the fixed
  dtschema, a schema whose only selector is properties.$nodename.const gets an
  auto-generated `select` (verified at runtime; thermal/thermal-zones.yaml and
  thermal/thermal-idle.yaml are the in-tree precedents, both in always_schemas with
  select {'properties': {'$nodename': {'items': [{'const': '<name>'}], ...}}}).
  The /rootparam schema therefore:

    $id    : http://devicetree.org/schemas/arm/huawei,rootparam.yaml#   (line 4)
    file   : 61 lines, in the disposable copy only
    selector: properties.$nodename: const: rootparam   (no compatible anywhere)
    declared properties, names and shapes kept exactly as observed:
        qcom,boardid      uint32-array, minItems 4, maxItems 4   (opaque)
        huawei,modem_id   uint32-array, minItems 2, maxItems 2   (opaque)
        qcom,board_name   string                                 (opaque)
        qcom,product_name string                                 (opaque)
        hardware_version  string                                 (opaque)
    required          : all five                                        (line 53)
    additionalProperties: false                                         (line 60)
    No hardware meaning, voltage, rail or calibration semantics is asserted for
    any value; every description says the value is opaque vendor metadata.
    The string properties use $ref /schemas/types.yaml#/definitions/string because
    the core meta-schema rejects a bare `type: string` in a binding (verified:
    dt-doc-validate reported "'string' is not one of ['boolean','object']" until
    the $ref form was used).

  Note on scope: this schema is a node binding, not a board binding. It does not
  participate in root compatible selection at all, so it cannot and does not
  substitute for the root compatible validation - that job stays with qcom.yaml.

5. WORK PACKAGE D - RECOMMENDATION AND LIMITS
--------------------------------------------------------------------------------
5.1 Recommendation
  Adopt Scheme 1 + the node-name-keyed /rootparam schema.

  Reasons, in evidence order:
  (a) It is the only mechanism in the fixed validator that resolves F1 while
      keeping arm/qcom.yaml applied to the root node (canary, 4.3).
  (b) It expresses the real pair exactly, in the order the DTB has it, with no
      fabricated compatible and no vendor substitution.
  (c) It requires no new top-level additionalProperties/unevaluatedProperties
      policy: one enum line, and the shipped file's own policy is left alone.
  (d) Registering a vendor board string in this file is the existing upstream
      pattern - huawei appears five times in the same file already (2.4).
  (e) It is one line against one file, which is reviewable and revertible.

  /rootparam handling: keep it out of the shared Qualcomm file. A separate schema
  selected by node name (no compatible) is the compliant way to constrain a vendor
  node that has no compatible; it keeps additionalProperties: false without opening
  anything, and it does not claim to validate the root node.

5.2 Can root compatible be expressed in the fixed dtschema without a broad
    top-level policy?  YES - via Scheme 1. The broad policy is never needed for
    the root node, because the root node is governed by arm/qcom.yaml, whose
    compatible oneOf is the intended registration point. A top-level `true` only
    ever appeared in drafts that tried to own the root node from a separate file.

5.3 Compliant handling of a compatible-less /rootparam  YES - node-name selection
    with a closed property set (3.4). Alternative reviewed and rejected: attaching
    the five properties to arm/qcom.yaml itself, which would put Huawei-specific
    vendor data into a shared Qualcomm board file and is not an acceptable
    upstream shape.

5.4 Evidence still missing before this can be merged upstream
  1. Huawei provenance for the exact string "huawei,dby-w09": vendor documentation
     or an accepted submission establishing it as the board compatible (the name
     currently exists only in the local draft DTS; it is not in any upstream file).
  2. Maintainer agreement for arm/qcom.yaml: that file is a Qualcomm board binding
     maintained upstream by its listed maintainer; a one-line addition still needs
     that review, and the submission must be a separate patch with a commit message
     naming the product.
  3. Upstream acceptability of a `rootparam` node binding at all: a vendor node
     with no compatible and a name that collides with no standard node is unusual;
     it may need either a huawei-prefixed node name in the DTS or an explicit
     documented rationale, and that decision affects the schema's selector.
  4. Provenance of the five rootparam values themselves (boardid, modem_id,
     board_name, product_name, hardware_version) - this task asserts only shape,
     so any semantic documentation needs a vendor source.
  5. A regression check that the enum insertion does not disturb the other
     sm8250 boards; the fixed corpus run shows no change for them, but an upstream
     submission would still need the full dt_binding_check/tree run.
  6. A decision on qcom,board-id/msm-id: both are upstream-deprecated yet present
     in this product's DTB, so their retention needs an explicit note rather than

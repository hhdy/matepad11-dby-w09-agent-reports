12. 与固定 ACK provider 行为的事实对照（只做对照，不含补丁建议）
--------------------------------------------------------------------------------
固定 commit 8ad08f75dd... 的 drivers/regulator/qcom-rpmh-regulator.c（只读查看）：

  事实 A：PM8150 L6 的 provider 定义
    文件内 pm8150_vreg_data[] 中有：
      RPMH_VREG("ldo6", "ldo%s6", &pmic5_nldo, "vdd-l6-l9")
    → 节点名 ldo6、RPMh 资源模板 "ldo%s6"、硬件描述 pmic5_nldo、
      supply 名称字符串 "vdd-l6-l9"。

  事实 B：pmic5_nldo 的硬件描述
      .regulator_type = VRM
      .ops            = &rpmh_regulator_vrm_drms_ops
      .hpm_min_load_uA = 30000        （即 30 mA，HPM 阈值）
      电压范围 320000 uV 起、步进 8000 uV、124 档
    → 与任务书 §5 所述“pmic5_nldo / rpmh_regulator_vrm_drms_ops / HPM 阈值 30 mA”一致。

  事实 C：supply 名称如何进入 regulator core
    rpmh_regulator_init_vreg() 中：
      vreg->rdesc.supply_name = rpmh_data->supply_name;
    → "vdd-l6-l9" 只是 provider 表里声明的 supply 名称；
      regulator core 会据此在该节点的 DT 中查找 "vdd-l6-l9-supply" 作为其 parent。
      本任务第 4/6/7 节已确认：base、九个 DTBO、九次合成后均无该属性，
      因此不存在 DT 层面的 parent regulator 指向。
      即：该字符串是 provider 侧的名称声明，不是已存在的物理上游供电网络证据。

  事实 D：qcom,always-wait-for-ack 的作用点
    rpmh_regulator_init_vreg()：
      vreg->always_wait_for_ack = of_property_read_bool(node, "qcom,always-wait-for-ack");
    rpmh_regulator_send_request()：
      if (wait_for_ack || vreg->always_wait_for_ack)
              ret = rpmh_write(...);          /* 同步等待 ACK */
      else
              ret = rpmh_write_async(...);    /* 异步发送 */
    rpmh_regulator_set_enable_state()：
      ret = rpmh_regulator_send_request(vreg, &cmd, enable);
    → 使能路径传入 wait_for_ack = true，禁用路径传入 wait_for_ack = false；
      因此 disable 是否等待 ACK 完全取决于该节点的 qcom,always-wait-for-ack
      （或调用方另行传入的 wait_for_ack）。
    set_mode 路径（rpmh_regulator_vrm_set_mode_bypass）固定传入 true。

  事实 E：load 与 mode 的关系
    rpmh_regulator_vrm_drms_ops 提供 .get_optimum_mode =
      rpmh_regulator_vrm_get_optimum_mode()：
        load_uA >= hpm_min_load_uA(30000) → REGULATOR_MODE_NORMAL，否则 REGULATOR_MODE_IDLE
    该 provider 的 ops 中没有 set_load / set_current_limit 回调，
    即消费者负载通过 regulator core 汇总后反映为 mode 选择（HPM/LPM），
    再由 set_mode 下发（该路径固定同步等待 ACK）。

  与本次 DT 事实合并后的对照结论（仅陈述事实，不作因果断言）：
    - HOS4.3 的静态 DT（base 全树 + 九个 DTBO + 九次合成）中，
      PM8150 L6 节点没有 qcom,always-wait-for-ack，
      故按上述 provider 代码，disable 走 rpmh_write_async 分支（除非有其它调用方
      显式传入 wait_for_ack=true）。
    - 该节点也没有任何 supply / coupling 属性，故在 DT 层面
      L6 没有 parent regulator，也没有与其它 regulator 的 coupling 声明；
      regulator core 不会因这些属性对 L6 做 post-decrement 式的父级投票扣减。
    - L6 在 regulator-core 中确实有消费者：UFS host 的 vccq 与 vddp-ref-clk
      （由 DTBO 提供）。因此 UFS 侧对 L6 的 enable/disable 会影响 L6 的
      consumer 计数；但 L6 自身没有父级可扣减。
    - 以上均为静态 DT/FDT 事实与 provider 代码路径的对照。
      不得据此推断 PMIC 的物理电源输入或电气原理图关系；
      不得据此断言控制器绝不等待 ACK（本报告只写“检查范围内未发现该属性”）；
      亦不据此判定 VDDP 清理已经安全。

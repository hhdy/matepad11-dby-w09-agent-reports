0. RESULT IN ONE PARAGRAPH
--------------------------------------------------------------------------------
The six target UFS rails exist in the HOS4.3 base boot FDT and are fully
identifiable by group compatible + qcom,resource-name + child regulator-name.
NONE of the four upstream regulator mode/DRMS property names
(regulator-initial-mode, regulator-allowed-modes, regulator-allow-set-load,
regulator-system-load) and NONE of the regulator-state-{standby,mem,disk} child
nodes exist anywhere in that FDT (global scan of all 3281 property-bearing
paths = 0 hits). HOS4.3 instead carries a vendor property set:
group-level qcom,regulator-type / qcom,supported-modes /
qcom,mode-threshold-currents / qcom,resource-name and child-level
qcom,init-mode / qcom,set. Those are reported rail-by-rail below with raw
values. No stock DTBO entry (0..8) contains any fragment that targets
/soc/rsc@18200000 or any descendant, and no entry contains any of the vendor or
upstream mode properties, so no stock overlay changes these rails. Symbolic
mode names, vendor driver semantics and all runtime behaviour remain
UNKNOWN / NOT_VERIFIED / NOT_RUN.

6. MODE NUMBER SEMANTICS - EXPLICIT NON-CLAIM
--------------------------------------------------------------------------------
The raw mode integers are reported, not symbolic names, because no audited
mode enum header is available inside this task's approved scope:
  - LDO-type rails (L5, L6, L9, L17) advertise supported-modes <2 4>.
  - SMPS-type rail (S8) advertises supported-modes <1 3>.
  - S4 advertises no supported-modes at all.
The LDO and SMPS enumerations do not overlap, so a single mode-number meaning
cannot be shared between them; any cross-type copy of a mode literal is unsafe
on this evidence alone. Mapping of 1/2/4 to any named mode is NOT_VERIFIED.
Structural pairing only: qcom,supported-modes and
qcom,mode-threshold-currents are equal-length ordered arrays on every rail that
carries them (2 entries each), so position i of the mode array corresponds to
the current threshold at position i. This is array-structure fact, not a mode
naming.

Numerical cross-check against ROUND47 (ACK side, separate source):
  - L5/L6/L9 threshold 30000 uA = 30 mA, equal to the ACK PMIC5 NLDO HPM
    threshold cited in ROUND47.
  - L17 threshold 10000 uA = 10 mA, equal to the ACK PMIC5 PLDO HPM threshold.
  - S8 threshold 200000 uA = 200 mA, on a PMIC5 HFSMPS type group.
These are numeric coincidences that support using the values as comparison
anchors; they do NOT establish that HOS4.3 and ACK make the same mode decision,
and they do NOT establish that the threshold is consumed at all on S8.
HOS4.3 does not encode a pldo/nldo distinction in DT (L17 and L5/L6/L9 all say
"pmic5-ldo"), so the ACK LDO sub-type assignment for L17 cannot be sourced from
this FDT.

7. WHAT THIS DOES AND DOES NOT SHOW
--------------------------------------------------------------------------------
Shown (static DT evidence only):
  - The six rails exist, are uniquely named, and are located in the apps_rsc
    (/soc/rsc@18200000) regulator groups.
  - HOS4.3 uses vendor mode metadata, not the upstream regulator-* property set.
  - Per-rail init-mode raw values differ: L5 = 4, L9 = 4, L6 = 2, L17 = 2,
    S8 = 1, S4 = absent.
  - Per-rail thresholds: 30000 / 30000 / 30000 / 10000 / 200000 uA; S4 absent.
  - No stock DTBO entry modifies any of these rails or their properties.
Not shown / not claimed:
  - Runtime PMIC mode, actual voltage, regulator enable state, consumer load,
    DRMS outcome, or any HOS ARC performance corner.
  - Any symbol name for mode values 1/2/3/4, or any statement that a rail is
    "in HPM" at boot. qcom,init-mode is reported as a raw initial-mode request
    field; its vendor driver semantics are NOT_VERIFIED here.
  - Any statement that S4 has no mode support in hardware; the FDT simply
    carries no mode metadata for it.
  - Any statement about the ACK post-overlay or runtime equivalence of these
    rails with ACK PM8150 ops.

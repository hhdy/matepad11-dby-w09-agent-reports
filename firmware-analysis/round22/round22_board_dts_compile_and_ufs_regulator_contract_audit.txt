5. Work package D — PM8150 VRM input parents and electrical assumption
--------------------------------------------------------------------------------
Source: common/Documentation/devicetree/bindings/regulator/qcom,rpmh-regulator.yaml,
common/drivers/regulator/qcom-rpmh-regulator.c,
common/drivers/regulator/core.c, final .config.

Binding definitions:
- pm8150-rpmh-regulators branch (yaml:282-294) lists grouped LDO input
  properties (vdd-l1-l8-l11-supply, vdd-l2-l10-supply, ... vdd-l13-l16-l17-supply)
  and patternProperties "^vdd-s([1-9]|10)-supply$": true.
- pm8150l-rpmh-regulators branch (yaml:159-175) lists vdd-bob-supply, grouped
  LDO supplies and patternProperties "^vdd-s[1-8]-supply$": true (covers S8).
- The top-level required: list (yaml:136-139) contains ONLY "compatible" and
  "qcom,pmic-id". All input-parent supply properties are optional schema
  properties. -> Missing vdd-s4/vdd-s8/... does NOT violate the binding.

Driver behavior:
- qcom-rpmh-regulator.c: RPMH_VREG(...) sets rdesc.supply_name to "vdd-sX"
  (e.g. :919 smps4 -> "vdd-s4", :988/:1020 smps8 -> "vdd-s8"). The driver does
  not itself require the parent; it hands supply_name to the regulator core.

Regulator core behavior:
- core.c:114-116: have_full_constraints() = has_full_constraints ||
  of_have_populated_dt(). On an arm64 DT boot the DT is populated, so this is
  true.
- core.c:2054-2096: when rdev->supply_name cannot be resolved, if
  have_full_constraints() the core substitutes dummy_regulator_rdev (a dummy
  parent); otherwise it defers/fails. No arm64 board calls
  regulator_has_full_constraints() explicitly (only legacy arm/x86 mach files
  and ACPI do), but of_have_populated_dt() already satisfies the condition.
- Final .config: CONFIG_REGULATOR=y, CONFIG_REGULATOR_FIXED_VOLTAGE=y,
  CONFIG_REGULATOR_QCOM_RPMH=y. (No REGULATOR_ALWAYS_DUMMY symbol in this tree.)

Answers to the five sub-questions:
1. Schema validity: NO — input parent properties are optional; omission is
   schema-valid for pm8150/pm8150l rpmh regulator nodes.
2. Driver registration/operation: NO hard requirement — the rpmh driver only
   declares supply_name; core resolves it. Registration succeeds with a dummy.
3. Dummy parent: YES — core.c:2079-2086 substitutes dummy_regulator_rdev when
   DT is populated and the supply is unresolved (dev_warn "...using dummy
   regulator").
4. Unresolved electrical assumption: a dummy parent means the physical input
   is assumed already present and enabled externally. It does NOT establish
   the board's real power tree, does not prove S4/S8 input rail identity,
   voltage headroom, or that the rail is powered at the right time. Any load
   vote or enable on such a rail is effectively unmanaged. This is exactly the
   pre-boot power-tree validation gate the draft flags (draft lines 137-143).
5. HOS4.3 data: ROUND11/14 found no vdd-s1..s10-supply, vin-supply or
   vph-pwr-supply in the inspected base-FDT scope; the five parent edges found
   are ARC virtual voltage-level / proxy links, not VRM electrical inputs.
   No safe physical rail mapping can be established -> keep UNKNOWN. Do NOT
   create vph_pwr=3.7V, fake fixed regulators, vdd-s*-supply or ARC-to-VRM
   translations. Data needed: a schematics/PMIC power-tree or an authorized
   post-ABL FDT capture that actually contains the VRM input supplies.

The draft's existing comments (lines 101-158, 218-241) already encode these
constraints correctly; no change is required to the regulator nodes for schema
or registration, only the electrical gate stays open.

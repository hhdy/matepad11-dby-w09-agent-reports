1. 工具与工作副本可用性（检测结果）
======================================================================
1.1 既有输出中是否存在 ramdisk 工作副本
- ROUND2 输出目录：存在 boot.img、dtbo.img、ramdisk.img、recovery.img、
  recovery_ramdisk.img、erecovery.img、erecovery_ramdisk.img 及 vbmeta 系列
  的本地镜像副本；这些是完整镜像，不是解包后的 ramdisk 内容目录。
- ROUND2 firmware_analysis.txt 记录的是镜像头部字段，未记录 boot.img 内
  ramdisk 区域的偏移量，也未导出任何 ramdisk 文件。
- ROUND3 输出：只有 super sparse / LP metadata 与 dtb_work 中的 FDT/DTBO
  工作副本；没有 ramdisk 内容文件、boot unpack 工具或 ramdisk 解析器。
- ROUND4 输出：只有 vendor / odm EROFS 镜像与 super 提取脚本；没有
  ramdisk 内容文件、boot unpack 工具或 ramdisk 解析器。
- 结论：NO_EXISTING_RAMDISK_WORKCOPY。

1.2 已审核过的 boot image 解析脚本
- ROUND2 使用的工作副本脚本（已审核、已修复 BOM 与路径问题）：
  Analyze-DBY-W09-Firmware.ps1。它有 Read-U32LE / Read-U32BE 读取镜像
  头字段的能力，并对 ramdisk*.img 调用 Get-FileMagic 做「完整文件级」
  魔数检测；它不包含 boot.img 内 ramdisk 区域的定位、提取或解包函数。
- ROUND3 的 Analyze-DBY-W09-DeviceTree.py 只在说明文字中描述 boot header
  v2 的 DTB 偏移公式，不解析 ramdisk。
- ROUND4 的两个 Python 脚本只处理 sparse / LP metadata。
- 结论：无可复用的、能安全读取 ramdisk 内容的已审核脚本。

2. ramdisk 格式与读取结果
======================================================================
- ramdisk 压缩格式：UNDETERMINED / BLOCKED。
  已审核脚本只对「完整文件」做魔数检测；boot.img 内的 ramdisk 是镜像内
  的一个区域，现有输出没有该区域的偏移量，没有已审核脚本能定位它。
  若要判定必须新增 boot image header 解析逻辑，按任务书第 3.A 节禁止，
  因此本子项停止，不写自制 parser，不猜 gzip/lz4/brotli。
- ramdisk 内容读取：NOT_RUN / BLOCKED。
  BLOCKED 原因（逐条）：
    B1 没有可信 boot unpack 工具（magiskboot / unpack_bootimg 均不存在）；
    B2 没有已审核的 ramdisk 区域定位/提取脚本可复用；
    B3 本机通用解压器（gzip/brotli/tar）不能替代 boot image 解析器；
    B4 任务书明确禁止自写 boot parser、禁止下载/安装未知 EXE/DLL、
       禁止 WSL 与绕过 Windows 安全策略；本轮遵守，不以任何方式绕过。
- ramdisk 文件 inventory：EMPTY（BLOCKED，未读取任何 ramdisk 文件，
  因此不编造 init*.rc / fstab.* / prop.default / ueventd*.rc 清单）。

  DTB address 32,505,856（数值仅作既有记录引用，不作为新证据）。

  并在该处校验 d00dfeed magic；本轮不重算、不重新定位。

7. 结论
======================================================================
ramdisk 在现有可信工具条件下不能安全检查：缺少 boot unpack 工具与已审核
的区域提取脚本，按任务书 fail-closed 原则判定 BLOCKED，不自制 parser。
既有 cmdline 记录中没有 panel/lcd/display selector；video=vfb 只是通用
framebuffer console 参数。没有 live FDT 或 runtime 证据，ACTIVE_PROFILE
继续 UNKNOWN。后续若要解除 BLOCKED，需要由任务下发方提供可信的 boot
unpack 工具与明确授权，而不是让本地 Agent 自行找工具或写解析器。

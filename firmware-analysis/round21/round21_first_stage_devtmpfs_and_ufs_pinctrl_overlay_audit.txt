ROUND21 - FIRST-STAGE /dev POPULATION AND UFS PINCTRL / DTBO
DEPENDENCY AUDIT - DBY-W09 (Honor Pad 9 / KONA / SM8250), HOS 4.3
======================================================================

Read-only, offline audit of already-existing ROUND18 and ROUND19 work
copies. No device, no ADB/fastboot, no rebuild, no config/DTS/DTBO edit.
All conclusions are bounded by the tool and evidence limits stated below.

----------------------------------------------------------------------
0. STATUS AND HEADLINES
----------------------------------------------------------------------

  A  first-stage /init static ELF / string / xref analysis ..... PASS
  B  base DTB + nine DTBO UFS-targeted mapping ................ PASS
  C  ACK Kconfig dependency + compatible cross-check ........... PASS
  D  decision matrix and next-build recommendation ............ PASS

Headlines:

  H1. The HOS4.3 standalone /init does NOT depend on kernel devtmpfs.
      FirstStageMain itself calls mount("tmpfs", "/dev", "tmpfs",
      MS_NOSUID, "mode=0755") (code reference at 0x2E5854), then creates
      five character nodes with mknod() and builds the rest of /dev from
      netlink uevents + sysfs regeneration. There is no "devtmpfs"
      string anywhere in 11,592 extracted strings and no symbol.
      ROUND20's "CONFIG_DEVTMPFS is not set" is therefore NOT a proven
      boot blocker for this exact userspace.

  H2. DEVTMPFS_MOUNT is also not needed. The pinned Kconfig help text at
      drivers/base/Kconfig:54-60 explicitly says initramfs-based booting
      must mount devtmpfs manually; this init is exactly that case and
      mounts tmpfs on /dev itself.

  H3. The base DTB enables neither UFS node by itself: both
      /soc/ufshc@1d84000 and /soc/ufsphy_mem@1d87000 carry
      status = "disabled". The nine DTBOs all carry two UFS fragments:
      fragment@63 enables the PHY and fragment@64 enables the host and
      supplies them from PMIC/RPMh/GDSC regulators.

  H4. Those two UFS fragments and all nine UFS-related __fixups__ are
      byte-identical across all nine board-id variants. Only the
      board-id root property differs. The 0x206a ("VG") entry remains a
      candidate only; runtime selection is UNKNOWN and no overlay was
      ever applied or merged in this round.

  H5. UFS rails do NOT require the Qualcomm TLMM pinctrl driver: every
      supply resolves to an RPMh regulator or the ufs_phy_gdsc GDSC.
      The base DTB does declare two UFS pinctrl states
      ("dev-reset-assert" / "dev-reset-deassert", pin "ufs_reset")
      under the TLMM node, but the pinned ACK 6.18.33 UFS driver does
      not look those names up; it uses reset_control() for core reset
      and an OPTIONAL device_reset GPIO that the base DTB does not
      provide. So TLMM is not proven necessary for UFS probe either.

  H6. A separate, more serious DT/driver mismatch was found: the HOS
      base DTB TLMM node is compatible = "qcom,kona-pinctrl", while the
      pinned ACK source contains only "qcom,sm8250-pinctrl" in
      drivers/pinctrl/qcom/pinctrl-sm8250.c:1357. Simply enabling
      CONFIG_PINCTRL_MSM (and even PINCTRL_SM8250) would NOT bind the
      HOS pinctrl node. This is reported as UNKNOWN U-4; no DTS was
      touched.

  H7. Next-build delta supported by evidence: DO NOT enable DEVTMPFS or
      DEVTMPFS_MOUNT merely because ROUND20 flagged them. If TLMM is
      wanted for other board consumers, it requires PINCTRL_MSM=y plus
      PINCTRL_SM8250=y plus a compatible-string decision that this
      round is not permitted to make. See section 5.

1.3 Tool limitation and how it was handled
  The installed binutils targets are x86_64 only (objdump --info lists
  elf64-x86-64 / i386 and no aarch64 backend). No llvm-objdump,
  aarch64 cross-objdump, gdb, radare2, capstone, pyelftools or keystone
  is installed, and installing any of them is forbidden.

  Therefore two small standard-library-only Python tools were written
  for this round:
   - tools/init_xref.py : partial fixed-width AArch64 decoder for
     ADRP / ADD(imm) / ADR / BL / B / CBz / TBz / MOVZ/MOVK x8 / SVC;
     recovers code-to-string cross-references and direct call edges.
   - tools/init_window.py : partial instruction-window printer for the
     same instruction forms.

  call targets. They are NOT a full disassembler and are never used to
  claim that an undecoded instruction has a particular effect.

  A major evidence upgrade was obtained without installing anything:
  the stripped /init carries a .gnu_debugdata section (XZ-compressed
  mini debug info). Python's built-in lzma decompressed it into a
  temporary copy; readelf then recovered 4,523 function symbols,
  including all android::init::FirstStage* C++ symbols. This converts
  the analysis from "strings might be dead" to "this exact function
  references this exact string".

2.3 Fallback behaviour
  After the tmpfs mount call, `cbz x0, 0x2E58E0` branches to a fatal
  log path (message at 0x209FF5, LogMessage construction at 0x41D044).
  No alternative mount source (notably no devtmpfs) exists in the
  decoded window or in the string/symbol set. Therefore:
    - mount(tmpfs,/dev) failure is FATAL, not silently tolerated;
    - there is no devtmpfs fallback to fall back to.

2.4 Answer to work-package question
  This exact /init REQUIRES kernel tmpfs (CONFIG_TMPFS=y in ROUND18) and
  a working mknod()/netlink-uevent/sysfs path. It does NOT require
  kernel devtmpfs. It cannot be decided from this binary whether the
  vendor's own kernel would still expose devtmpfs for other reasons;
  that is outside the pinned ACK tree and no device evidence exists.

2.5 Package A limitations
  - The decoder is partial: only the instruction forms in 1.3 are
    decoded. Branches through function pointers, tail calls through
    registers, and instruction forms outside the decoder are not
    claimed to be understood.
  - No source for this exact HOS /init is available, and the private
    same-device DerpFest implementation is out of scope by standing
    instruction; no search was attempted.
  - Dynamic execution, emulation and device execution are forbidden;
    therefore runtime ordering of uevent arrival vs. first mount is
    not observed, only the static call structure.

  The already-decompiled DTS texts from ROUND19 were parsed with a
  small read-only Python brace/property parser (tools/ufs_dts_audit.py).
  Phandles in the base were resolved to node paths by matching
  `phandle = <0x..>`; overlay external fixups were read from each

  were combined, and no board-id was treated as selected.

3.6 Does the resulting tree need Qualcomm TLMM for UFS probe or rails?
  - Rails: NO. Every UFS rail resolves to an RPMh regulator or a GDSC;
    none resolves to a pinctrl/GPIO provider.
  - UFS host probe in the pinned ACK source: NOT PROVEN. The host
    driver (drivers/ufs/host/ufs-qcom.c) uses reset_control_assert/
    deassert on `core_reset` (lines 440-470, 512-513) and an OPTIONAL
    device_reset GPIO via gpiod_set_value_cansleep (lines 726-734).
    The base UFS node has no reset-gpios, so that GPIO is absent.
    A full-tree search found ZERO occurrences of the state names
    "dev-reset-assert" / "dev-reset-deassert" in the ACK source. The
    generic pinctrl core looks up PINCTRL_STATE_DEFAULT ("default",
    drivers/pinctrl/core.c:2174), which is not one of these names.
  - The two state nodes nevertheless exist in the DT and are referenced
    by pinctrl-0/pinctrl-1. Any consumer that tries to apply them
    needs a working provider for "qcom,kona-pinctrl". See U-4.
  - No UFS crypto-specific DT node was found. "ufs_ice" occurs only as
    a reg-names entry in the host and PHY nodes; the separate
    /soc/qcrypto@1de0000 node is "qcom,qcrypto" and is not part of
    the UFS fragment set.

3.7 Package B limitations
  Only the already-decompiled DTS texts were used. dtc's decompilation
  can normalise label names and byte-string escapes; the exact original
  source formatting is not recoverable. The audit is deliberately
  scoped to UFS host/PHY/rails/pinctrl/phandles, not a full-tree
  inventory (ROUND19 already did that and is not repeated).

4.3 The compatible-string mismatch (new in ROUND21)
  The HOS base DTB TLMM node (package B) declares exactly:
      compatible = "qcom,kona-pinctrl"
  A full-tree search of the pinned ACK source found "qcom,kona-pinctrl"
  ZERO times in .c/.h/.dts/.dtsi/.yaml. The only SM8250-related pinctrl
  compatible in the driver is:
      drivers/pinctrl/qcom/pinctrl-sm8250.c:1356-1359
        static const struct of_device_id sm8250_pinctrl_of_match[] = {
            { .compatible = "qcom,sm8250-pinctrl", },
            { },
        };
  and the in-tree DTS uses the same string at
      arch/arm64/boot/dts/qcom/sm8250.dtsi:5111
      Documentation/devicetree/bindings/pinctrl/qcom,sm8250-pinctrl.yaml:17

  The "older DeviceTree compatibility" comment in pinctrl-msm.c:1453
  concerns gpio-ranges handling, NOT compatible-string fallback; there
  is no alternative match entry that would accept "qcom,kona-pinctrl".
  drivers/pinctrl/pinctrl-single.c:1983 matches "pinctrl-single", which
  is also not present on the HOS TLMM node.

  Consequence: even after enabling PINCTRL_MSM and PINCTRL_SM8250, a
  stock HOS DTB with only "qcom,kona-pinctrl" would not be claimed by
  the ACK driver. Resolving this requires a DT-side or driver-side
  compatible decision, which this round is forbidden to make.

4.4 UFS driver's actual pinctrl/reset dependency
  drivers/ufs/host/ufs-qcom.c:
    - lines 440-470: ufs_qcom_host_reset() calls
      reset_control_assert/deassert on host->core_reset. This maps to
      the base UFS node's resets = <0x17 0x21> / "core_reset", i.e.
      the GCC reset provider, not TLMM.
    - lines 512-513: host reset is part of the normal host path.
    - lines 726-734: ufs_qcom_device_reset_ctrl() treats the device
      reset GPIO as OPTIONAL ("reset gpio is optional") and returns if
      host->device_reset is NULL. The base UFS node has no reset-gpios,
      so this path is inactive in this DTB.
    - ZERO references to pinctrl_get_select / pinctrl_lookup_state or
      to the two state names in drivers/ufs/*.
  drivers/pinctrl/core.c:2174 looks up PINCTRL_STATE_DEFAULT ("default")
  for generic pin binding; the UFS node's states are named
  "dev-reset-assert" and "dev-reset-deassert", so generic default-state
  binding does not apply to them either.

  Therefore, on the evidence available, the missing TLMM driver is NOT
  proven to block UFS probe or UFS rail control. It remains a real
  platform-level gap for other board consumers and a compatibility
  mismatch (U-4), not a demonstrated first-stage UFS blocker.

4.5 Package C status
  PASS for the requested Kconfig/dependency/compatible review. The
  conclusion "enabling only the Kconfig symbol is not enough" is
  positively demonstrated by 4.3, not inferred.

6. UNKNOWNS AND THE EVIDENCE THAT WOULD SETTLE THEM
----------------------------------------------------------------------

  U-1  Runtime ordering of uevent arrival versus first-stage mount.
       Static call structure is known, timing is not. Needs a boot log
       from the device; out of scope here.

  U-2  Whether the vendor HOS kernel's own UFS driver consumes the
       "dev-reset-assert"/"dev-reset-deassert" pinctrl states. The
       pinned ACK driver does not (zero string hits), but the vendor
       driver source is not available. Needs the vendor driver source
       or a disassembly of its kernel module.

  U-3  Whether a dynamically constructed "devtmpfs" string exists in
       /init outside the decoded instruction forms. No literal and no
       symbol exists; needs a complete AArch64 disassembler plus a
       full control-flow analysis, which cannot be installed here.

  U-4  Which compatible the TLMM node should present to ACK 6.18.33.
       HOS DTB says "qcom,kona-pinctrl"; ACK only matches
       "qcom,sm8250-pinctrl". Needs an authorised DT/driver decision or
       a vendor binding document. This is the highest-value open item
       for any future TLMM work.

  U-5  Which of the nine DTBOs is selected in a given boot. ROUND19
       established board IDs and candidate 0x206a; no same-boot
       evidence exists. Needs a device-side dump of the applied DTB.

  U-6  Whether DEVTMPFS is enabled for unrelated consumers in the
       vendor kernel (not in the pinned ACK build). Does not affect
       this /init conclusion but would change a full-system picture.
